weld, the linker

weld links relocatable objects into an executable, in place of ld, lld or mold. Dynamic executables on x86_64 Linux work through the gcc driver today. Static glibc, shared libraries and dynamic linking on the other architectures do not.

Install

The crate is lamina-weld; the binary it installs is weld. The newest release{{#if weld_version}}, {{weld_version}},{{/if}} is older than the source this page describes, so cargo install lamina-weld does not get the current behavior. That source needs Rust 1.88 (its manifest sets rust-version = "1.88"). From a checkout, run cargo install --path weld. There are no feature flags.

With the Lamina driver

$ lamina app.lamina -c weld
$ lamina app.lamina --assembler ras -c weld

In place of ld

Use a prefix directory holding an ld symlink and point the compiler at it with -B. Unlike ras, weld does not look at argv[0]; the symlink is only there so the driver finds it. The argv[0] claim was not tested.

$ mkdir -p toolchain
$ ln -sf "$(command -v weld)" toolchain/ld
$ ln -sf "$(command -v ras)" toolchain/as
$ gcc -B"$PWD/toolchain/" hello.c -O2 -o hello

That builds a position-independent executable through both of our tools, with gcc supplying the CRT objects and the interpreter path as it does for any linker.

-fuse-ld=weld does not work. gcc only accepts the linker names it was built to know, and clang rejects it the same way. -B is the way in.

Flags it accepts

Everything gcc's collect2 passes on a normal Linux link is accepted, which is why the -B route works at all.

FlagBehaviorNotes

-o -e -l -LTakenOutput, entry symbol, library, library path. Joined and separate forms both parse.

-staticTakenResolves archives only. Produces ET_EXEC with no interpreter and no dynamic symbols.

-pie -no-pieTakenAccepted on all three architectures. On aarch64 the PIE names /lib/ld-linux-aarch64.so.1 as its interpreter, which was not run here. -static -pie together is an error.

--start-group --end-groupTakenArchive cycles resolve to a fixed point.

-rpath --dynamic-linkerTakenrpath entries join into one DT_RUNPATH.

--gc-sections -s -MapTakenSection GC, strip, map file.

--as-needed --eh-frame-hdr --hash-style= -z -pluginParsed, no effectAccepted so a driver's command line does not fail. -z takes its value separately, so -z now parses and -zrelro does not.

-shared -r --relocatableErroris not supported yet. weld cannot produce a shared object.

anything elseErrorunrecognized option. This catches -T, -soname, --sysroot, -export-dynamic and --no-undefined.

Formats and architectures

FormatStaticDynamic

ELF64x86_64 aarch64 riscv64PLT, GOT and DT_NEEDED are written for x86_64 only. A -l on aarch64 or riscv64 ends in undefined symbol.

Mach-Ox86_64 arm64Mach-O executables are written and checked with file. Whether dyld and libSystem load, and whether the output is ad-hoc codesigned, was not run: there is no macOS host here.

PE32+x86_64COFF input must be AMD64. Any COFF input produces a PE32+ executable, whatever the output name.

ELF input is ELF64 little-endian only, so -m elf_i386 and 32-bit objects are refused.

Where it is not a drop-in

Static glibc failsgcc -static stops at static GNU IFUNC is not supported: __new_memcpy; resolver calls require IRELATIVE relocations and startup relocation tables. glibc selects its string and block-copy routines through IFUNC resolvers, and nothing emits IRELATIVE yet. -static is for freestanding objects and plain archives.

No shared libraries-shared is refused, so weld cannot build a .so.

Dynamic linking is x86_64 onlyaarch64 and riscv64 link statically and as PIE, but have no PLT or GOT construction.

Entry point on aarch64 and riscv64With no _start defined, weld's synthetic startup stub is written for x86_64 only. The other two fall back to entering at main, which is wrong without a CRT.

clang AArch64 objects with unwind tablesunsupported AArch64 relocation type 261, which is R_AARCH64_PREL32 in .eh_frame. Building with -fno-asynchronous-unwind-tables gets past it.

Quiet failuresA failed link often prints only weld: link failed. An unknown -e symbol falls back silently, a missing -l is dropped without a message (checked on a static output), and -v needs RUST_LOG=info to show anything.

Interpreter path is assumedWithout --dynamic-linker weld writes the glibc path. A musl system needs it passed. The gcc driver passes it anyway. Not run on musl.

Archives need an indexarchive has no index; run ranlib to add one. Taken from the source; not run in this pass.
