Output and I/O

A Lamina program writes output in one of two ways. It can write bytes itself with writebyte and write, which need no libc. Or it can declare a C function such as printf with @extern and call it, which links libc.

The I/O contract

The four I/O instructions return an integer. The value tells you what happened:

InstructionSuccessEnd of inputError

writeNumber of bytes writtennot applicable-2

readNumber of bytes read. 0 when the size is 0.-1, when no bytes were available-2

writebyte1not applicable-2

readbyteThe byte, 0 to 255. A zero byte is data, not end of input.-1-2

The values are integers. The surface does not state their width; treat them as 64-bit signed. Builds that predate this contract may return different values for end of input and for errors, so check for -1 and -2 only with a build that implements it.

Writing bytes

writebyte sends one byte to standard output. This program writes Hi and a newline:

fn @main() -> i64 {
  entry:
    %a = writebyte 72
    %b = writebyte 105
    %c = writebyte 10
    ret.i64 0
}

Formatting a number is the frontend's job, so Lamina has no instruction for it. This helper writes an unsigned number in decimal, one digit at a time, using only writebyte. It prints 31415:

fn @put_digit(i64 %n) -> i64 {
entry:
  %ascii = add.i64 %n, 48
  %w = writebyte %ascii
  ret.i64 0
}

fn @put_u64(i64 %n) -> i64 {
entry:
  %small = lt.i64 %n, 10
  br %small, last, more
more:
  %hi = div.i64 %n, 10
  %lo = rem.i64 %n, 10
  %r = call @put_u64(%hi)
  %d = call @put_digit(%lo)
  ret.i64 0
last:
  %e = call @put_digit(%n)
  ret.i64 0
}

fn @main() -> i64 {
entry:
  %a = call @put_u64(31415)
  %nl = writebyte 10
  ret.i64 0
}

Reading and writing buffers

write takes a pointer and a byte count and returns how many bytes it wrote. read does the reverse. This program copies standard input to standard output one byte at a time, and stops when readbyte reports end of input:

fn @main() -> i64 {
  entry:
    jmp loop
  loop:
    %b = readbyte
    %eof = eq.i64 %b, -1
    br %eof, done, emit
  emit:
    %w = writebyte %b
    jmp loop
  done:
    ret.i64 0
}

The loop tests the result against -1, not against zero, so a zero byte in the input does not end it.

Through libc, with printf

Declare the function with @extern. A declaration ending in ... is variadic, so this is how printf and its relatives are called. Arguments past the named ones follow the C promotion rules: an f32 is passed as an f64. This program prints 2.50 and a newline:

@extern
fn @printf(ptr %fmt, ...) -> i32

global $fmt: [7 x i8] = "%.2f\n"

fn @main() -> i64 {
  entry:
    %f = getelem.i8 $fmt, 0
    %r = call @printf(ptr %f, f64 2.5)
    ret.i64 0
}

A global array is not a pointer. getelem.i8 $fmt, 0 takes the address of its first byte, which is the value printf expects. Linking this program links libc, because printf is provided by it.

An indirect call through callptr needs the ... marker at the call site, because the call has no declaration to read it from:

%p = funcaddr @printf
%r = callptr.i32 %p(ptr %f, ..., i32 42)
Output is not buffered

writebyte, write and the other I/O instructions are system calls. There is no stdio layer under them, so each call is its own write. The libc route goes through printf, which is buffered by libc as usual.
