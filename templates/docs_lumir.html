LUMIR

Lamina has two intermediate forms. You write the first, the IR. The compiler lowers it to the second, LUMIR, and all optimization and code generation happen there. This page explains the second form and why it exists.

The pipeline

.lamina text  →  IR (parsed)  →  LUMIR  →  machine code
                 lamina-ir        lamina-mir    per-target codegen

IR is the text you write, parsed into named types, aggregates and high-level instructions. LUMIR is the lower form. Its values are virtual registers, its types are machine types, and its merges are copies placed on control-flow edges. Every backend reads LUMIR.

What differs

AspectIRLUMIR

ValuesNamed locals such as %x, each a slot with one typeVirtual registers such as v0, numbered per function

TypesNamed types, aggregates and !Name structsScalar and vector machine types

MergesAssignment to the same name on each pathCopies placed on the edges between blocks

Addressesgetelem and getfieldptr with a layoutBase plus offset, or base plus index times scale

CallsTyped argumentsArguments classified by the target ABI, with stack slots assigned

Target decisionsNoneMade here, per target

Why it is separate

A text format you write by hand should be readable, stable from one release to the next, and free of machine detail. An intermediate form that the optimizer and the backends work on should say exactly which register, which addressing mode, and what the calling convention does with a 16-byte struct. Forcing one form to do both makes each worse. The split keeps the text stable while the lower form changes.

Reading a LUMIR dump

Write the dump with --emit-mir. The output is written next to the input with a .lumir extension and the compiler exits. For this program:

fn @put_digit(i64 %n) -> i64 {
entry:
  %ascii = add.i64 %n, 48
  %w = writebyte %ascii
  ret.i64 0
}

fn @main() -> i64 {
entry:
  %a = call @put_digit(7)
  ret.i64 0
}
$ lamina digit.lamina --emit-mir
$ cat digit.lumir

The dump names each function and block, keeps the source labels where it can, and writes each instruction with an explicit type. Registers appear as v0, v1 and so on. A value's type is written on the instruction, and memory operations carry the alignment their type requires. Once the frame is laid out, stack slots appear as offsets from the frame.

A LUMIR dump has no named types, because they are resolved to their layouts.

Optimization levels

--opt-level selects how much the LUMIR optimizer does, from 0 to 3. The default is 1. The optimizer runs on LUMIR, so an --emit-mir dump at a given level shows the result of that level. The option is marked experimental in the driver.

$ lamina digit.lamina --emit-mir --opt-level 0
$ lamina digit.lamina --emit-mir --opt-level 3

What this page does not cover

LUMIR is not a stable interchange format. Its text may change between releases, and it is not a language to write by hand. Write IR, and read LUMIR only to see what the compiler did.
