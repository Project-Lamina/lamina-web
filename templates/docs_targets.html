Backends

Targets and backends

What a target supports is a list of features, not a score. x86_64 and AArch64 carry the whole feature set. RISC-V 64 and PowerPC64 carry everything except aggregates by value, which they refuse rather than lower to a guessed ABI. The rest emit text nobody has executed.

Executed targets

These are compiled, run, and diffed against recorded output. The first three run on a CI job on that operating system; the last three run under qemu-user by hand.

TargetStatusNotes

x86_64_linuxTestedThe reference path, and the only one where every feature is exercised. SysV: aggregates up to 16 bytes in registers, larger ones in memory, hidden return pointer in rdi.

x86_64_windowsTestedWin64 passes aggregates of 1, 2, 4 or 8 bytes by value and everything else by reference. The hidden return pointer goes in rcx and shifts the other arguments along.

aarch64_macosTestedApple Silicon. AAPCS64: integer aggregates up to 16 bytes in registers, larger ones returned through the caller's buffer in x8.

aarch64_linuxTestedSame ABI as macOS, cross-executed under qemu at -O0 through -O3. Through the assembler: the direct binary encoder still misses IntConvert and Copy.

riscv64_unknownPartialScalars, control flow, and callptr run. No aggregate ABI. RV64 only; riscv32_unknown has never been executed.

powerpc64_linuxPartialELFv2, same gap as RISC-V. Locals sit above the 64-byte parameter save area, which a variadic callee such as printf is entitled to overwrite.

What each backend can lower

A backend refuses what it cannot classify. An unsupported aggregate is a compile error naming the function, never a silently wrong ABI.

FeatureWhere it worksNotes

Integer scalars, control flow, callseverywhereThe common path. Every published backend lowers it.

Integer aggregates by valuex86_64 aarch64RISC-V, PowerPC64, WebAssembly and the GPU backends refuse the module instead of guessing a classification.

Float or mixed aggregatesnowhereA struct with a float field is refused on every target, x86_64 included.

Calls through a pointerx86_64 aarch64 riscv64 powerpc64WebAssembly refuses callptr: nothing emits a function table yet.

Direct binary emissionx86_64 aarch64x86_64 is complete. AArch64 covers a subset and falls back to the assembler.

JIT into executable memoryx86_64Nightly feature. Calls and multi-block functions are still open.

Experimental target identifiers

These have code-generation support in the source tree and nothing behind it. Assembly comes out; no job has assembled, linked or run it, so nothing past the text is known.

How to read this list

Target parsing, code generation, assembly, and linking are separate stages. A recognized identifier does not promise an end-to-end compiler path.

Driver acceptanceThe command-line parser recognizes more identifiers than this public matrix. Recognition alone is not a support claim.

AArch64 binary emissionThe direct encoder covers part of the instruction set. Assembly-based workflows do not depend on it and are fully supported.

Experimental register allocationGlobal linear-scan and graph-color allocation are not available for every backend. The default allocator remains the practical choice.
