Targets and backends

What a target supports is a list of features, not a score. x86_64 Linux is the reference and has every feature on this page. Everything else is a cross target. The rows below say what was run and what was not. Each feature a target lacks is refused by name, not lowered to a guess.

Targets

The driver accepts nineteen architectures in a default build. Eighteen of them emit code; arm32 is accepted and then refuses, naming the target. Three more architectures exist only behind the nightly Cargo feature and are not available targets; they are listed under Nightly only and nowhere else. What each target can and cannot do today is below. Where a limit is listed, the compiler refuses at compile time and names the function; it does not emit a silently wrong ABI. Pass counts are deliberately not given here: they change with every commit and say nothing about whether a target suits you. Each row has a full entry further down, with its argument registers, its refusals, how it is assembled and linked, why its limits sit where they do, and what evidence stands behind the claim.

Names the compiler accepts

A target name passes three checks, in order. The parser reads the name and fails on anything it does not know. The driver then refuses any name that is not in its own list of target names, which is the list printed under Supported values. A name that passes both goes to a backend, and the backend either lowers it or refuses it by name. Every row below was produced by running the release compiler with --target on a one-function program. Where a name is not in a row, it was not run.

Each row has one of these states. Supported and Partial rows link to a full entry above where one exists. Accepted, unverified means the compiler writes an artifact but nothing here shows that the artifact works. Accepted, not implemented means the name is accepted and the compilation stops with the refusal shown. Rejected on purpose and Nightly only are described under their own headings. Evidence is stated with the same terms as How to read this list.

Rejected on purpose

A name is refused here when accepting it would mean emitting something other than what it says. Each refusal carries a hint naming the spelling to use instead, so the message is the documentation.

ppc64-elfv1, powerpc64-elfv1Big-endian POWER here is ELFv2. ELFv1 calls through .opd function descriptors and is a different ABI, not a byte order. The hint names ppc64.

mips, mipsel, mips32, mips32elThe N64 ABI is implemented on 64-bit MIPS only, not O32. The hint names mips64 and mips64el.

s39064-bit z/Architecture only. The hint names s390x.

openbsd, netbsd, dragonflyThere is no syscall table, dynamic linker path or ELF brand for any of them. FreeBSD is the BSD that is implemented, and the hint names it.

ppc64 is no longer refused. It names the big-endian POWER target, which has a backend; see the names table above.

Nightly only

Three architectures and one operating system parse only in a build with the nightly Cargo feature. In a default build each is Unknown architecture or Unknown operating system. None of them is an available target, and none appears in the tables above.

arx64An experimental 64-bit architecture of this project's own. There is no silicon for it and there is no assembler for it, neither ras nor GNU. Code generation writes assembly text and nothing consumes that text. It is not a chip you can target.

riscv128128-bit RISC-V, which is itself a draft. The target carries a 128-bit pointer width so the rest of the compiler has to state what it does with one; that is what it is for.

lisaParses behind the feature and is in no driver list, so --target lisa_linux is refused even on a nightly build.

arteryAn operating-system name for the Artery kernel. It parses and nothing else is wired to it.

An identifier that parses on a nightly build and not on a default build is not a supported target. Anything behind the feature may change or disappear without notice.

Operating systems

The operating-system part of a name changes the output in only a few ways. The table below gives each name that changes something and each name that is accepted but changes nothing. The rest are refused by the driver with Unsupported target, and the refusal produces no output at all. A name such as x86_64_freebsd does not get FreeBSD output, and it does not get Linux output under another name either.

linuxThe reference. ELF output, symbols without a prefix, CFI directives. x86_64 and riscv64 link with weld. aarch64 and ppc64le fall back to GNU ld, which needs a cross C library.

macosMach-O output. Every symbol gets a leading underscore (_main), and the .note.GNU-stack section is not written. Verified for x86_64 and aarch64 by assembly diff, and by file on the produced executables.

windowsx86_64 only, a PE32+ .exe from ras and weld. Symbols are not prefixed. The CFI directives and the .note.GNU-stack section are not written. Not executed. aarch64_windows is refused at assembly.

ios, tvos, watchos, visionosThe assembly carries the macOS underscore prefix, but neither ras nor GNU as writes these object files, so no executable is produced for any of them. visionos is accepted only with aarch64.

android (x86_64, aarch64), horizon (aarch64 only)Accepted with no change to the assembly, which is identical to linux. Linking takes a GNU fallback with a [WARN]. x86_64_android writes an ELF with the interpreter path noted above, so it does not start here. aarch64_android and aarch64_horizon stop at the missing C library.

orbis (ps4), prospero (ps5)On x86_64 only. The assembly is identical to linux. Linking takes the GNU fallback, and the executable has the same interpreter path as android. Nothing in the output is specific to the console.

wasiOn wasm32 only. It adds an exported _start that calls main. wasm32_unknown has no such export. The rest of the module is the same.

cuda, amdhsaThese select the GPU backends, nvptx64_cuda and amdgcn_amdhsa. Other combinations with those architectures are refused.

freebsdOn x86_64 only. x86_64_freebsd compiles and links. bsd is a spelling of the same name. The other BSDs are refused at the parser with a hint naming this one, because there is no syscall table, dynamic linker path or ELF brand for them.

Where the parser and the driver differ

The parser accepts more names than the driver. A name the parser accepts and the driver does not list is refused with Unsupported target and no reason. The reason is shown only when the parser itself fails, so x86_64_freebsd gets no explanation at all. Library code that calls the parser directly gets the wider set. The driver's list is the set that works from the command line. lamina --help names no targets in full. Its sub-architecture line gives examples, and the parser also accepts aarch64v8.1, armv7m, armv7a-sf and ppc64le-power10.

Semantics that do not vary by target

The things that usually differ quietly between architectures were checked against each backend and match. A frontend can rely on these without a per-target branch, which is the point of writing them down.

Overflowadd, sub and mul wrap on every target. One evaluator, IntBinOp::evaluate, serves the interpreter and the constant folder, so a folded constant and a computed value agree.

Shift countsMasked to the operand width on every backend rather than left to the ISA, which disagrees about wide counts. Measured on x86_64: shl.i32 %a, 33 emits shlq $1.

Division by zeroTraps everywhere, as does MIN / -1. x86_64 lets idivq raise it and adds an explicit guard for the narrow MIN / -1 case; aarch64 emits cbnz … udf #0; riscv emits bnez … .word 0; ppc64, armv7 and loongarch64 share the same check. Measured on x86_64: a program dividing by a runtime zero exits 136, which is SIGFPE.

i128 divisionGuarded in the shared wide lowering, so the guard is the same on every backend: both halves of the divisor are ORed to detect zero, and the signed MIN / -1 case is caught by comparing both words.

Float to integerTruncates toward zero, saturates to the target range, and turns NaN into zero — on x86_64, aarch64, riscv64 and ppc64 alike, and matching the interpreter. This is the classic silent cross-architecture divergence and it does not exist here. It is also why i686 refuses the conversion outright rather than shipping a different answer: x87 reports an out-of-range or NaN operand as the integer indefinite, which is not the saturating result the contract names.

Atomic orderingAll five orderings are carried from the IR through MIR to the backend one for one, and aarch64, riscv64 and ppc64 each consult the ordering per operation. A backend that cannot do atomics refuses the module; none of them silently drops to a weaker ordering.

Optimizer and atomicsNo pass reorders, deletes or CSEs an atomic or a volatile access. Dead-code elimination treats every atomic and fence as side-effecting, memory forwarding clears its tables at any atomic or fence, CSE matches only arithmetic and comparison, LICM lists atomics as side-effecting, and both mem2reg and SROA refuse a slot an atomic touches.

Target by target

The same six questions for each target, so they can be read side by side. ABI is what a frontend must match. Lowers and Refuses are what the backend does with the IR; a refusal names the function and stops, which is the behaviour to prefer over a wrong ABI. Toolchain is what assembles and links it. Evidence says how the rest of the entry is known, and nothing is called tested without saying by what.

x86_64_linux

The reference. Every other backend is written against behaviour first established here, which is why a feature missing elsewhere is almost always "not yet written for that backend" rather than "impossible there" — the IR does not have target-conditional semantics. It is also the only target where a program that uses the C library goes from .lamina to a running binary without a tool Lamina did not write.

ABISystem V AMD64. Integer and pointer arguments in rdi rsi rdx rcx r8 r9, then the stack; floating point in xmm0–xmm7. Integer results in rax, with rdx for a second eightbyte; float results in xmm0. An integer aggregate up to 16 bytes travels in up to two integer registers; one larger than that is copied into the caller's argument area, and a large result is written through a hidden pointer the caller supplies. Callee-saved: rbx rbp r12 r13 r14 r15. Frames are rounded to a multiple of 16, so rsp is 16-byte aligned at every call.

LowersInteger and float scalars, integer aggregates by value, atomics including atomic_cmpxchg and fences, bit intrinsics, 128-bit vectors from the text IR, variadic calls, variadic definitions, inline assembly, i128, indirect calls, float-to-int and int-to-float in both signednesses.

RefusesAn aggregate with a float field, which no target accepts yet: aggregate not yet supported: %p of @sum has a float field; only integer aggregates cross a boundary so far. The refusal is raised in MIR lowering, before any backend sees it, which is why it reads the same everywhere. Under --sandbox, a function of more than one block: x86_64 JIT encoder currently supports only single-block functions.

Toolchainras assembles and weld links, with no host tool involved. This is the only target where that holds for a program that uses the C library.

EvidenceRun natively on this machine: compiled, assembled, linked and executed, with output and exit status checked.

DefectsNone recorded. -g produces real source lines: a hello-world build carries .debug_line through ras and weld, and the decoded table maps addresses to the right lines of the .lamina file.

x86_64_windows

The same instruction selection as x86_64_linux with a different calling convention bolted to it, so the arithmetic, atomics and aggregate handling are the Linux target's and need no separate trust. What differs is argument placement and, as a consequence, variadic functions: the variadic implementation is built around the System V register save area, where a callee spills its six integer and eight vector argument registers into a known 176-byte block and va_list walks it. Win64 has no such block — it spills into the caller's shadow space instead — so the backend refuses va_start rather than reuse a layout that does not describe the machine.

ABIWin64. Integer arguments in rcx rdx r8 r9, floating point in xmm0–xmm3, and the two banks share one positional slot each — a double in the second parameter position travels in xmm1 whatever came first. Aggregates of 1, 2, 4 or 8 bytes go by value and everything else by reference. The hidden return pointer takes rcx and pushes the other arguments one slot along. Callers reserve 32 bytes of shadow space. 16-byte aligned at the call.

LowersThe same scalar, aggregate, atomic, bit-intrinsic, i128 and indirect-call set as the Linux target, plus variadic calls.

RefusesA variadic definition: variadic arguments are not yet supported on Windows x64; only System V. Float aggregates, as everywhere.

Toolchainras and weld, both of which handle the PE format. Compiling for it from this Linux host produces a .exe with no host assembler or linker and no warning.

EvidenceCompiled, assembled and linked here; not executed, as nothing on this machine runs a PE binary. Treat the Win64 argument rules as read from the backend rather than observed in a running program.

DefectsNone recorded beyond the variadic gap. The absence of a run is the real limit on this entry: an ABI mistake of the kind that only shows at a C boundary would not have been caught.

aarch64_macos

Not a separate backend. It is aarch64_linux with Mach-O output, underscore-prefixed symbols, and the two places AAPCS64 differs on Darwin: a named stack argument is packed at its natural size and alignment instead of taking a whole eight-byte slot, and a variadic callee is handed every variadic argument on the stack whichever registers are still free. Everything in the aarch64_linux entry below applies here, including its defect.

ABIAAPCS64, Darwin variant. Arguments in x0–x7 and d0–d7; an integer aggregate up to 16 bytes in registers, a larger result written through a buffer whose address arrives in x8. Named stack arguments are packed, not slotted. Callee-saved: x19–x28 plus x29 and x30. 16-byte aligned at the call.

LowersAs aarch64_linux: scalars, integer aggregates, atomics, bit intrinsics, i128, indirect calls, variadic calls, 128-bit vectors on NEON.

RefusesA variadic definition: variadic argument `va_start v1` is not yet supported by the AArch64 backend. Inline assembly. Float aggregates.

Toolchainras and weld, both of which handle Mach-O. A Mach-O executable builds cross from this Linux host with no host tool and no warning.

EvidenceCompiled, assembled and linked here; not executed, as nothing on this machine runs a Mach-O binary. The Darwin-specific argument rules are read from the backend, not observed.

DefectsInherits the 16-byte argument alignment gap described under aarch64_linux, for the same reason.

aarch64_linux

The most complete cross target: everything a program normally needs lowers, and the two refusals are features rather than correctness gaps. The one thing to be careful of is argument alignment. The placement loop counts argument registers by word and never rounds that counter up for an argument that needs a wider alignment — armv7's placement does exactly that rounding and AArch64's does not — so the only type where it shows is the only one with a 16-byte alignment requirement, i128. The result is a misplaced parameter rather than a refusal, which makes it the most dangerous thing on this page.

ABIAAPCS64. Integer and pointer arguments in x0–x7, then the stack; floating point in d0–d7 from a bank of their own. Integer results in x0 and x1, float results in d0. An integer aggregate up to 16 bytes travels in registers; a larger result is written through a buffer whose address the caller passes in x8, and the callee keeps that address alive across its own calls. Callee-saved: x19–x28, x29, x30. The frame pair is pushed with stp x29, x30, [sp, #-16]!, keeping sp 16-byte aligned.

LowersInteger and float scalars, integer aggregates by value, atomics and fences with the ordering honoured per operation, bit intrinsics, i128, indirect calls, variadic calls, float-to-int and int-to-float, 128-bit vectors on NEON.

RefusesA variadic definition, naming the instruction: variadic argument `va_start v1` is not yet supported by the AArch64 backend. Inline assembly: inline assembly is not yet supported by the AArch64 backend; it is x86_64 Linux only — an asm operand is bound to a physical register from an x86_64 pool before the template runs, and no other register file has that wiring, so the backend refuses rather than pass the text through unbound. Float aggregates.

Toolchainras assembles. weld does not link it, and says so: [WARN] weld cannot link Aarch64 Linux yet; linking with GNU aarch64-linux-gnu-ld instead. The GNU linker then needs a cross C library, which is not installed here, so the link stops at cannot find -lc.

EvidenceCompiled and assembled here; not executed. The link cannot complete without a cross C library, and that is also why it was not run under qemu — the emulator is installed, the libraries are not. The ABI claims come from the backend and from reading the emitted assembly.

Defects16-byte argument alignment is not honoured. AAPCS64 requires an argument of 16-byte alignment to start on an even register, and it does not: for fn @g(i64 %a, i128 %b) the i128 is placed in x1:x2 where a C compiler puts it in x2:x3. Any call that crosses into C with an i128 parameter after an odd number of words reads the wrong value, with no diagnostic.

riscv64_unknown

Feature for feature the closest thing to aarch64_linux, but it does not share that target's argument-alignment defect. The RISC-V psABI applies the even-register rule to variadic arguments only; a named 2*XLEN scalar takes the next register pair with no skip, which is what this backend does and what clang does. It is also the only cross target weld links by itself, which makes it the one place the whole Lamina toolchain can be exercised away from x86_64 — but only for a program that calls nothing from the C library, because weld has no cross libc to resolve against. A program that prints falls back to GNU ld and then stops for want of that library. The unknown in the name is the operating system, meaning freestanding; it does not mark the target as speculative.

ABILP64D. Integer and pointer arguments in a0–a7, then the stack; floating point in fa0–fa7. Integer results in a0 and a1, float results in fa0. An integer aggregate up to 16 bytes travels in registers; a larger result is written through a hidden pointer that takes a0 and pushes the real arguments along. Callee-saved: s0–s11, saved in pairs. The locals area is rounded up so sp keeps the 16-byte alignment the ABI requires.

LowersInteger and float scalars, integer aggregates by value, atomics and fences with the ordering honoured per operation, bit intrinsics, i128, indirect calls, variadic calls, float-to-int and int-to-float.

RefusesA variadic definition: RISC-V backend does not support variadic arguments yet. Inline assembly: inline assembly is not supported by the RISC-V backend; it is x86_64 Linux only. Vectors: V extension is required for vectors on rv64imafd. Float aggregates.

VectorsThere is an RVV lowering in the backend and no way to reach it. The V extension cannot be written in an ISA string — rv64gcv is unknown RISC-V extension letter — so no target spelling turns V on and every vector compile for RISC-V stops at the message above. Read the RVV emitter as written but not wired up.

Toolchainras assembles. weld links it, and is the only cross target where that is true — but only while the program needs no C library symbol. A program that calls write stops at [WARN] weld cannot link: undefined symbol write; linking with GNU riscv64-linux-gnu-ld instead, and the GNU linker then fails on the missing cross C library.

EvidenceCompiled, assembled, and for a libc-free program linked all the way to an ELF executable by weld — further than any other cross target gets here. Still not executed to a correct result: the freestanding binary has no startup code and faults when the entry function returns, so the run proves the link, not the code. Anything that prints cannot be linked here at all.

DefectsThe ELF produced by weld is marked soft-float by file although the backend generates LP64D code and hardware fadd.d; the float ABI flag in the header does not match what is inside it, which will matter the moment it is linked against anything else.

ppc64le_linux and ppc64_linux

Both byte orders, one backend. ppc64le is little-endian and ppc64 is big-endian; both are ELFv2, and the endianness is a target property the lowering reads, not a separate code path. What is refused is the other POWER ABI: ppc64-elfv1 is rejected at the parser, because ELFv1 calls through .opd function descriptors, which is a different calling convention and not a byte order. The frame is the other thing worth knowing: ELFv2 requires a 64-byte parameter save area below the locals, and it is not optional padding, because a callee such as printf spills its own register arguments into the caller's save area. Locals placed there would be overwritten by a call.

ABIELFv2 in both byte orders. Integer and pointer arguments in r3–r10, floating point in f1–f13; every argument occupies doublewords of the parameter save area whether or not it travelled in a register. Integer results in r3. The frame carries a 32-byte linkage area and a 64-byte parameter save area below the locals. Frames are 16-byte aligned. Functions carry both a global and a local entry point, with .localentry marking the distance between them.

LowersInteger and float scalars, integer aggregates by value, atomics and fences with the ordering honoured per operation, bit intrinsics, i128, indirect calls, variadic calls, float-to-int and int-to-float.

RefusesThe architecture spelling ppc64-elfv1, before anything is compiled: Architecture 'ppc64-elfv1' is not supported — Hint: big-endian POWER here is ELFv2. ELFv1 calls through .opd function descriptors and is a different ABI. Write 'ppc64' (e.g. ppc64_linux). A variadic definition: PowerPC64 backend does not support variadic arguments yet. Inline assembly: inline assembly is not supported by the PowerPC64 backend; it is x86_64 Linux only. Vector operations: PowerPC64 vector operations — there is no VSX or AltiVec lowering. Float aggregates.

ToolchainNeither half is Lamina's. [WARN] ras has no PowerPC encoder; assembling with GNU powerpc64le-linux-gnu-as instead, then [WARN] weld cannot link PowerPC64 Linux yet; linking with GNU powerpc64le-linux-gnu-ld instead. The big-endian target uses the powerpc64-linux-gnu prefix for both. Start-up objects come from the target's own cross gcc, not the host's.

EvidenceCompiled and assembled by GNU as, which is worth more than a compile alone: a real assembler accepted every instruction, operand form and relocation the backend emitted. Not linked and not executed, here or under qemu, for want of a cross C library.

DefectsNone recorded. Unlike aarch64 and riscv64, the 16-byte-aligned argument is placed correctly: an i128 after one integer argument starts at r4, which is the even register ELFv2 asks for.

s390x_linux

The first big-endian target, which is what it was added for: everything that had quietly assumed little-endian byte order had to state its answer before this backend could emit anything. It has no register allocator. Every virtual register lives in a frame slot and operands are shuttled through a fixed handful of scratch registers, so the code is large and slow and obviously correct in a way that a half-written allocator would not be. Asking for a global allocator is refused rather than ignored. Linux is the only operating system it accepts.

ABIz/Architecture ELF, big-endian, 64-bit pointers. Integer and pointer arguments in %r2–%r6, floating point in %f0, %f2, %f4, %f6, then the stack. Integer results in %r2, float results in %f0. Every frame carries a 160-byte register save area at the bottom, which the prologue fills with stmg %r6,%r15. %r11 is the frame pointer and %r15 the stack pointer; %r0 is never used, because it reads as zero in an address. The stack is 8-byte aligned at a call, not 16.

LowersInteger and float scalars, integer aggregates by value, indirect calls, variadic calls, float-to-int and int-to-float. Division uses the even-odd register pair the hardware requires.

RefusesAtomics and fences: s390x atomic operations and fences. Bit intrinsics: s390x integer bit intrinsics (popcount, ctlz, cttz, bswap). Integer rotates. Vectors: s390x vector operations — there is no z/Architecture VX lowering. Inline assembly. A variadic definition: s390x variadic argument access. Any register allocator but the incremental one, and any operating system but Linux, each by name.

ToolchainNeither half is Lamina’s. ras has no z/Architecture encoder, so assembly goes to GNU s390x-linux-gnu-as; weld does not link s390x, so the link goes to s390x-linux-gnu-ld with -m elf64_s390 and /lib/ld64.so.1 as the interpreter. The start-up objects come from s390x-linux-gnu-gcc, not from the host compiler. That distinction used to be wrong and it is the reason this target did not work: a cross link got no crt1.o at all, so -e _start resolved to nothing, the linker fell back to the first function in .text, and the program never reached __libc_start_main or exit. It now links the target’s own start-up objects, and a cross gcc that cannot be found is an error naming the missing file rather than a binary that runs wrong.

EvidenceCompiled. The ABI is covered by unit tests over argument classification, frame sizes and call areas. Not assembled, linked or executed as part of this page, and there is no end-to-end run for s390x anywhere in the compiler’s own tests.

Defectslibgcc is not added to a cross link, so a program that needs an i128 helper such as __divti3 has an unresolved symbol at link time.

mips64_linux and mips64el_linux

One backend, two byte orders, same as POWER. The 32-bit O32 ABI is not implemented and the spelling mips is refused with a hint rather than mapped onto the 64-bit one, because O32 passes arguments differently and a program built under the wrong name would be wrong at every call. Feature for feature this is the same backend as s390x: the two were written together and refuse the same list.

ABIN64. Integer and pointer arguments in $4–$11, floating point in $f12–$f19, positionally alongside them, so an argument takes the register matching its first doubleword whatever its class. Integer results in $2, float results in $f0. $25 holds the address of the function being called, which is how a position-independent callee derives its own global pointer. $30 is the frame pointer and $29 the stack pointer; the saved return address and frame pointer sit at the top of the frame.

LowersInteger and float scalars, integer aggregates by value, indirect calls, variadic calls, float-to-int and int-to-float.

RefusesAtomics and fences, bit intrinsics, integer rotates, vectors (mips64 vector operations — no MSA lowering), inline assembly and a variadic definition, each by name. Linux is the only operating system.

Toolchainras has no MIPS encoder. GNU mips64-linux-gnuabi64-as and mips64el-linux-gnuabi64-as, then GNU ld with -m elf64btsmip or -m elf64ltsmip and /lib64/ld.so.1.

EvidenceCompiled, with ABI unit tests as for s390x. Not assembled, linked or executed here.

loongarch64_linux

The least exercised target on this page, and the reason is circular rather than technical: nothing on a normal development machine assembles LoongArch64, so no build here gets past the assembler, so no mistake in the emitted text is ever caught, so nobody extends it. Its refusal list is not a list of hard problems — atomics, bit intrinsics and aggregate passing are all straightforward on this architecture and are implemented on the other 64-bit targets. They are simply the parts not yet written, and the backend names each one rather than emit something plausible. Read its assembly as a draft.

ABILP64D in shape: integer and pointer arguments in $a0–$a7, floating point in $fa0–$fa7, results in $a0 and $fa0, frame pointer $fp established above a 16-byte-aligned $sp. Aggregate passing is not implemented, so there is no aggregate rule to match.

LowersInteger and float scalars, control flow, direct calls, indirect calls, variadic calls, float-to-int and int-to-float, division with the shared zero and MIN / -1 checks.

RefusesAggregates by value, naming the function: LoongArch64 does not yet pass aggregates by value, as @make_pair does. Atomics: LoongArch64 atomic operations and fences. Bit intrinsics: LoongArch64 integer bit intrinsics (popcount, ctlz, cttz, bswap). A variadic definition: LoongArch64 variadic argument access. Inline assembly: inline assembly is not supported by the LoongArch64 backend. i128, which is modelled as a 16-byte aggregate and so hits the aggregate refusal naming @__divti3 — the helper the wide lowering wants to call.

Toolchainras has no LoongArch64 encoder and no cross assembler is installed here, so the build stops at ras cannot assemble LoongArch64 Linux; no GNU as is installed for LoongArch64 (looked for loongarch64-linux-gnu-as). With that assembler present it would fall through to it, and then to GNU ld.

EvidenceCompiled only, not executed, and not even assembled: the assembly text was produced and read and nothing else touched it. Nothing on this page is weaker evidence than that.

DefectsNone recorded, which reflects how little has been exercised rather than how much works. Treat the assembly as unverified until some assembler has accepted it.

armv7_linux

A 32-bit target with a 64-bit integer problem and a hard-float ABI, and the two interact. Because armv7 has no 64-bit registers, an i64 is legalized into a pair of 32-bit ones, and MIR models that pair as an eight-byte integer aggregate. That representation is why its one known defect exists: at a return, the backend cannot tell a legalized i64 from a real eight-byte struct, and AAPCS wants opposite things for them — registers for the integer, memory for the composite. It chooses registers, on the stated grounds that getting a 64-bit integer wrong would be the costlier mistake, and a five-to-eight-byte struct pays for it. The floating-point side is the other thing to match carefully: floats live in a bank of their own and never touch r0–r3, except when the call is variadic, where the base standard applies instead and a double travels in core registers after all.

ABIARM state, AAPCS in the VFP hard-float variant. Core arguments take r0–r3 and then the stack; floating point takes s0–s15 and d0–d7 from a bank of its own, back-filled. Once one co-processor argument misses the bank the rest of the bank is closed and later floats go to the stack, never into core registers. A variadic argument is placed by the base standard, so a double handed to printf travels in an even core pair or on the stack. An argument of 8-byte alignment rounds the core register number up to an even one — the rounding AArch64 and RISC-V are missing. A result of up to two words comes back in r0:r1; anything larger through a buffer whose address arrives as a hidden first argument in r0. Callee-saved: r4–r11 and d8–d15. The prologue masks sp with bic sp, sp, #15, so it is 16-byte aligned. Needs a Cortex-A7 or later, because it uses hardware sdiv and udiv rather than calling a division helper for 32-bit operands.

LowersInteger and float scalars, integer aggregates by value, indirect calls, variadic calls, bit intrinsics, float-to-int and int-to-float, 64-bit integers legalized into register pairs with __divdi3 and __udivdi3 from the C library for division.

RefusesAtomics: armv7 backend does not implement atomic operations, and for a 64-bit one the refusal comes earlier, from the pair legalizer, with the reason: an atomic operation on a 64-bit integer on a 32-bit target: two words cannot be read or written atomically without a double-word atomic. Inline assembly, which stops in MIR lowering as an unsupported instruction. The va_* family in a definition. i128: names a 128-bit integer on a 32-bit target: that takes four registers, and only pairs are split. An indirect call whose argument or result is 16 bytes wide: an indirect call carries no callee signature to pass a 16-byte aggregate by, so call the function directly — the classification needs a declared parameter type and a function pointer does not carry one. Float aggregates.

Toolchainras has no armv7 encoder and no cross assembler is installed here: ras cannot assemble Armv7 Linux; no GNU as is installed for Armv7 (looked for arm-linux-gnueabihf-as). With that assembler present it would fall through to it, then to GNU ld.

EvidenceCompiled only, not executed. Assembly text is produced and read; nothing assembles, links or runs it here, including under qemu. The ABI description comes from the placement code and from reading the emitted prologues, where the register and VFP assignments are visible directly.

DefectsA composite of 5 to 8 bytes is returned in r0:r1 where AAPCS says memory, so a C caller of such a function reads the wrong value. This is the deliberate trade described above, not an oversight, and it will stay until MIR can distinguish a legalized integer pair from a genuine composite.

thumbv6m and thumbv7m

Cortex-M, bare-metal ELF, Thumb only. There is no ARM state on a Cortex-M, so the choice the armv7 backend made — A32, where every data-processing instruction is conditional and a boolean needs no IT block — is not available here. The only conditional data-processing instructions this backend emits are a conditional set and a conditional move, and on ARMv7-M each writes the IT and the one instruction it guards together, so the block is always one instruction long and its pattern always matches. ARMv6-M has no IT at all, and there the same two helpers branch over one instruction instead. No other IT is emitted anywhere.

The frame is addressed from the stack pointer, which the prologue sets once and nothing moves afterwards; the widest outgoing argument area any call needs is reserved there too. That is what makes ARMv6-M workable, where a load against a general register reaches 124 bytes but one against the stack pointer reaches 1020.

ABIAAPCS, soft float, 32-bit pointers, 8-byte stack alignment at a call. The two targets differ by instruction set: thumbv6m is ARMv6-M, Thumb-1, a Cortex-M0 or M0+; thumbv7m is ARMv7-M, Thumb-2, a Cortex-M3, M4 or M7. armv6m and cortex-m0 are spellings of the first; armv7m and cortex-m3 of the second.

LowersInteger scalars up to 32 bits, control flow, direct and indirect calls, recursion, integer aggregates by value.

RefusesFloating point, by name and with the reason: the M0 has no FPU, and the single-precision VFP an M4F or M7 may carry is not used here, so the message is does not implement floating point rather than a soft-float libcall to a library nothing ships. A hard-float variant spelling is refused for the same reason. 64-bit integers, until the legalization pass splits them into register pairs for this backend. Atomics, vectors, inline assembly and variadic definitions. On ARMv6-M additionally: integer division, which the instruction set does not have, and any access whose declared alignment is narrower than its type, which would take a HardFault. A function named like a Thumb register is refused, because bl r0 reads as an instruction rather than a symbol.

ToolchainAssembly text only. ras has no Thumb encoder, and the Cortex-M toolchain is arm-none-eabi, which is not a GNU Linux triple, so the driver has no cross assembler to fall back to either. Both _unknown and _linux are accepted and produce bare-metal ELF assembly; no other operating system is.

EvidenceCompiled only. The assembly has been read; nothing here assembles, links or runs it.

i686_linux

The 32-bit x86 target, and the one whose limits follow from a single missing piece. armv7 and rv32 both run the LUMIR pass that splits a 64-bit integer into a pair of 32-bit registers; i686 does not, and its backend refuses anything that needs one rather than truncate. That single gap is why it cannot return an i64, and since __divdi3 itself returns one, why it cannot divide a 64-bit integer either — the refusal arrives naming the helper, which is confusing until you know the chain. The second limit is unrelated and will not be fixed by that pass: i686 uses x87 for floating point, and x87 reports an out-of-range or NaN operand as the integer indefinite rather than saturating. Since every other backend saturates and maps NaN to zero, honouring the conversion here would mean shipping a different answer on one target, so it refuses instead. Note also that no callee-saved register is ever touched: every virtual register lives in a frame slot and values move through %eax, %ecx and %edx, which is what six general registers afford.

ABIcdecl, which is 32-bit System V. Every argument goes on the stack, each rounded up to a four-byte word, and the caller cleans up — with one exception: a callee that returns through a hidden struct pointer releases that pointer itself with ret $4, which is what the i386 convention asks of it. Integer results in eax, a 64-bit result in edx:eax, floating point on the x87 stack. Callee-saved: ebx esi edi ebp, none of which the backend uses. The stack is 16-byte aligned at the call: call pushes four bytes onto an aligned esp and the prologue pushes ebp, leaving it eight past a boundary, so the frame is sized to 8 mod 16 to put it back on one.

Lowers32-bit integer and float scalars, control flow, direct calls, indirect calls, variadic calls, bit intrinsics.

RefusesReturning a 64-bit integer, naming the function: i686 return of @main: a 64-bit integer comes back in %edx:%eax, and 64-bit integers are not yet legalized into 32-bit register pairs. Any 64-bit division, through the same message naming @__divdi3. Float-to-int, with its reason: i686 float to integer conversion is not implemented: x87 reports an out-of-range or NaN operand as the integer indefinite, not as the saturating result the contract names. Atomics: i686 atomic operations and fences are not implemented. Inline assembly. A variadic definition. i128, through the four-register message. An indirect call carrying a 16-byte aggregate. Float aggregates.

ToolchainNeither half is Lamina's: [WARN] ras cannot assemble I686 Linux; assembling with GNU as instead, then [WARN] weld cannot link I686 Linux yet; linking with GNU ld instead. Both tools are the host's own binutils, driven with --32 and -m elf_i386, so no cross toolchain is needed on an x86_64 machine.

EvidenceRun here: compiled, assembled, linked and executed. The binary is a 32-bit ELF and runs on this x86_64 host through 32-bit compatibility, printing correctly and returning the right exit status. It is a real run, but not a run of Lamina's own toolchain and not on a 32-bit machine.

Defects-g numbers instructions instead of emitting source lines. x86_64 emits .loc 1 3 5 for the statement the instruction came from; i686 emits .loc 1 1 0, .loc 1 2 0, .loc 1 3 0 and so on, counting upward with no relation to the .lamina file. A debugger will step through it, but the lines it shows are fiction.

riscv32_linux and riscv32_unknown

These two spellings are not variants of the same thing, and confusing them wastes an afternoon. The backend is shared; what differs is whether a C library exists, which decides what happens the moment a program divides a 64-bit integer.

ABIILP32D in shape. Integer and pointer arguments in a0–a7, floating point in fa0–fa7, results in a0 and fa0, sp 16-byte aligned. A 64-bit integer is legalized into a pair of 32-bit registers.

Lowers32-bit integer and float scalars, integer aggregates by value, 32-bit atomics, control flow, direct calls, 64-bit integers as register pairs.

The differenceDivision of a 64-bit integer needs __divdi3 or __udivdi3. On riscv32_linux those come from the C library and the backend emits the call. On riscv32_unknown there is no C library, and rather than emit a call that cannot link, the compiler refuses: `__udivdi3` is a compiler runtime helper that a target without a C library does not provide; define it in the module, or name an implementation with LAMINA_BUILTINS=__udivdi3=<symbol>. The refusal names the way out, and it is the same mechanism for any runtime helper. A great many programs divide somewhere, so on the freestanding spelling that refusal surfaces far more often than its narrow wording suggests.

RefusesBoth spellings refuse: i128, through names a 128-bit integer on a 32-bit target: that takes four registers, and only pairs are split. 64-bit atomics: an atomic operation on a 64-bit integer on a 32-bit target: two words cannot be read or written atomically without a double-word atomic. va_arg of an i64: a variadic slot holds one word, and reading the pair is not implemented. A variadic argument wider than one word, named at the call site: a variadic i64 argument to @printf spans two rv32imafd registers, which this backend does not yet place, and the same for an f64. Bit intrinsics: RISC-V32 backend does not support integer bit intrinsics yet. Float-to-int: RV32 float to integer conversion is not supported. Indirect calls: Riscv32 does not yet call through a pointer, as @main does. Inline assembly. Float aggregates.

Toolchainras writes no riscv32 object, and no cross assembler for it is installed here, so a build stops at the assembler. For an end-to-end rv32 path, there is none today.

EvidenceCompiled only, not executed, on both spellings. Nothing assembled, linked or run.

DefectsNone recorded separately from the refusals above. For 64-bit work on RISC-V, use riscv64_unknown.

wasm32 and wasm64

WebAssembly is the one target with no calling convention to match, because it has no registers: a function's signature is its ABI, and locals live in the module's own locals plus a shadow stack in a mutable global. The pairing of widths catches people out. wasm32 has 32-bit pointers and wasm64 64-bit, but both have native 64-bit integers, so a 32-bit pointer does not imply 32-bit arithmetic and an i64 needs no legalization on either. That same design is behind the defect below: the backend holds every integer value as a wasm i64 internally — constants, arithmetic, results — and the declared signature of an imported function is generated from that internal view rather than from the IR type. Aggregates are refused for a different reason: with no registers there is no classification to apply, so passing a struct by value would mean inventing a memory and copy convention, and that decision has not been made.

ABIThe function's wasm signature. Locals live in the module's locals and a shadow stack held in a mutable global $sp that starts at the end of the first page. wasm64 declares a memory64 memory and indexes it with i64. There is no aggregate rule, because aggregates do not cross a boundary by value. Three spellings exist: wasm32_wasi, wasm32_unknown and wasm64_unknown; there is no wasm64_wasi.

LowersInteger and float scalars including i64 on both widths, control flow, direct calls, indirect calls through a function table where a function address is its table index, variadic calls, float-to-int and int-to-float, 128-bit vectors on simd128. wasm32_wasi writes its own digits, prints through fd_write and exports _start. The freestanding spellings import env.writebyte from the host instead, so a plain wasm runtime cannot run them alone — the host has to supply that import.

RefusesAggregates by value, naming the function and the width: Wasm32 does not yet pass aggregates by value, as @make_pair does, and the same for Wasm64. Atomics, naming the instruction: WASM backend: instruction not yet supported: atomic_store.i32 1, [[v0]] seqcst. Bit intrinsics: WASM backend does not support integer bit intrinsics yet. Variadic definitions: WASM backend does not support variadic arguments yet. Inline assembly: inline assembly is not supported by the WASM backend; it is x86_64 Linux only. On the freestanding spellings, a runtime helper such as __divti3, through the same no-C-library refusal rv32 gives.

ToolchainThe backend emits WAT text, which wat2wasm then assembles. That tool is not on this machine, so a build here stops at Failed to spawn wat2wasm and only --emit-asm completes. Neither ras nor weld is involved; there is nothing for them to do.

EvidenceCompiled only, not executed: WAT is produced and read, and nothing assembled it to a .wasm or ran it under a wasm runtime. The defect below was found by reading the emitted module's import section against the IR it came from.

DefectsAn imported function's integer parameters and results are declared i64 whatever the IR said. fn @f(i32 %a) -> i32 declared @extern is imported as (func $f (param i64) (result i64)), and a function declared to return i32 is defined with (result i64). A host that exports the function the IR describes will not instantiate the module. Pointer parameters are not affected and come out correctly: on wasm32 a ptr parameter is declared (param i32) and on wasm64 (param i64), which is right for each.

nvptx64_cuda and amdgcn_amdhsa

These are not binary targets and should not be read as unfinished versions of one. A GPU backend emits text for a GPU toolchain to take further, so there is no linker step to be missing and no C ABI to match. The two refusals that stop most programs follow from the execution model rather than from unwritten code: a module with no @kernel has no entry point a device can launch, and globals have no meaning until a memory space is chosen for them — which is also why a program that merely prints a string is refused, since the string is a global.

ABINo C calling convention to match. PTX declares kernel parameters in a parameter space — .visible .entry add(.param .u64 .ptr .global .align 1 arg0) — and AMDGPU emits an HSA kernel with its own metadata. There are no argument registers, no callee-saved set and no stack alignment rule for a frontend to honour. --mcpu selects the AMDGPU processor, gfx900 or gfx1200.

LowersInteger arithmetic, memory operations, control flow and threading, inside a function marked @kernel.

RefusesA module with no kernel, before anything else: GPU code emission: functions must be marked as kernels. Globals: PTX does not yet support global variables and AMDGPU does not yet support global variables, which rules out most programs written for the other targets. Aggregates by value, naming the function. Atomics. Inline assembly.

ToolchainNeither ras nor weld, and no linker. The output is a text artifact — a .ptx file for NVIDIA, a .s file for AMD — that a GPU toolchain takes from there. There is no linked binary to produce and none is attempted.

EvidenceCompiled only, not executed. A kernel compiles and the PTX was read; nothing was assembled by a GPU toolchain and nothing was run on a device.

DefectsNone recorded. The missing global-variable support is the limit worth planning around.

What each backend can lower

The same information across the other axis, for choosing a feature rather than a target. A backend refuses what it cannot classify. An aggregate it has no rule for is a compile error naming the function, never a silently wrong ABI.

FeatureWhere it worksNotes

Integer scalars, control flow, direct callseverywhereThe common path. Every published backend lowers it, including both wasm widths and, inside a kernel, the GPU backends.

On armv7 and rv32 they are legalized into register pairs, with __divdi3/__udivdi3 for division. i686 does not run that legalization pass, so it refuses to return one, which also rules out that division helper.

A pointer to one is a scalar and works anywhere.

Vectors, 256-bitnowhere<8 x i32> parses and validates, and every backend then refuses it. On x86_64 the message is x86_64 V256 requires AVX and it appears at every CPU level, v3 and v4 included. aarch64 and wasm say V256 is unsupported; neither has a 256-bit register. 512 bits and wider are refused in IR validation as no register width.

Per-lane vector shiftsx86_64 v3, aarch64shl.<4 x i32> %a, %b with a vector %b is one count per lane; with a scalar it is one count for every lane. x86_64 needs AVX2 for the per-lane form and says so: x86-64-v2 has one count for all lanes and nothing else, with a hint to splat the count instead. wasm has no per-lane form at all.

Vectors across a callnowhereA vector type may be an instruction suffix and the type of a value. It may not be a parameter, a return type, a struct field, a global or a stackalloc, and IR validation refuses each by name. A helper that works on vectors takes a pointer. Nobody has written the per-target vector calling convention down.

i128x86_64 aarch64 riscv64 ppc64leDivision is guarded in the shared wide lowering, so the trap behaviour is the same on all four. The 32-bit targets refuse it: four registers, and only pairs are split. loongarch64 and WebAssembly refuse it as a 16-byte aggregate. On aarch64 and riscv64 it is also the type that exposes the argument-alignment defect.

Calling a variadic functionx86_64 aarch64 riscv64 ppc64le loongarch64 armv7 i686 wasmWorks nearly everywhere, because a call site only has to place the arguments. rv32 refuses an argument wider than one word, naming the callee.

Defining a variadic functionx86_64 Linux (System V)Harder than calling one: the callee has to spill its argument registers into a save area and va_list has to walk it, and that layout is per-ABI. Only the System V one is written, so every other target refuses, each naming itself. Win64 refuses too.

Inline assemblyx86_64 LinuxAn asm operand is bound to a physical register from an x86_64 pool before the template runs, so there is nothing to reuse on another register file. Other targets refuse the module; AArch64, RISC-V, PowerPC64, LoongArch64 and WebAssembly each name themselves, and on the 32-bit targets it stops earlier, in MIR lowering, as an unsupported instruction.

Float to integerx86_64 aarch64 riscv64 ppc64le loongarch64 armv7 wasmSaturating, NaN to zero, identical on every backend that has it. i686 and rv32 refuse rather than differ.

Source-line debug infox86_64-g emits .file/.loc and ras writes minimal ELF DWARF. On x86_64 the decoded line table matches the .lamina source. On i686 the line numbers are an instruction count.

JIT into executable memoryx86_64, default CLI buildThe in-memory encoder handles single-block functions. --sandbox refuses a multi-block one by name: x86_64 JIT encoder currently supports only single-block functions; 'main' has 4 block(s). Plain --jit falls back to a temporary executable and runs it correctly. The JIT also refuses some return types that the ahead-of-time path accepts.

How to read this list

Target parsing, code generation, assembly, and linking are separate stages. A recognized identifier does not promise an end-to-end compiler path.

Driver acceptanceThe parser recognizes more names than the driver accepts, and the driver accepts more names than this matrix describes. Many operating-system names are accepted and change nothing; Names the compiler accepts says which. Recognition alone is not a support claim.

What the evidence row meansFour phrases appear above and they are not interchangeable. Run natively: compiled, linked and executed on this machine, with output and exit status checked — x86_64_linux, and i686_linux through 32-bit compatibility on the same host. Assembled: a real assembler accepted every instruction the backend emitted, which is weaker than a run but catches a malformed operand or relocation — ppc64le, and the ras-assembled cross targets. Compiled only, not executed: assembly text was produced and read and nothing else touched it. Not exercised: nothing at all. No target was run under qemu for this page. Qemu user-mode emulation is installed; what is missing is the cross C libraries, so the programs never link far enough to hand it anything.

Toolchain fallback is announcedWhen ras or weld cannot handle a target, the driver says so on stderr with a [WARN] and uses the GNU tool named in that message. It never falls back silently. If no suitable host tool is installed, the build stops with an error naming the tool it looked for. -c gnu, -c clang and --assembler override the choice explicitly.

Where weld and ras standweld links x86_64 on Linux, Windows and macOS, aarch64 on macOS, and riscv64 for a program that needs no C library symbol. ras assembles x86_64 on all three operating systems and aarch64 and riscv64 on ELF; PowerPC64, LoongArch64, armv7, i686, rv32, WebAssembly and the GPU targets go elsewhere. The pairing that is Lamina's own end to end, for a program that uses libc, is x86_64 Linux.

Experimental register allocationGlobal linear-scan and graph-color allocation are not available for every backend. The default allocator remains the practical choice.

Nightly identifiersA few architectures exist only behind the nightly feature and are not described here. An identifier that parses on a nightly build and not on a release build is not a supported target.
