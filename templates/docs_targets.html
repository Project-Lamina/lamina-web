Targets and backends

What a target supports is a list of features, not a score. x86_64 Linux is the reference and has every feature on this page. Everything else is a cross target. The rows below say what was run and what was not. Each feature a target lacks is refused by name, not lowered to a guess.

Targets

The driver accepts eighteen architectures in a default build and all eighteen emit code. arm32 was the nineteenth and is now refused where the target string is parsed, with a hint naming armv7; it is no longer an advertised target. Three more architectures exist only behind the nightly Cargo feature and are not available targets; they are listed under Nightly only and nowhere else. What each target can and cannot do today is below. Where a limit is listed, the compiler refuses at compile time and names the function; it does not emit a silently wrong ABI. Pass counts are deliberately not given here: they change with every commit and say nothing about whether a target suits you. Each row has a full entry further down, with its argument registers, its refusals, how it is assembled and linked, why its limits sit where they do, and what evidence stands behind the claim.

Names the compiler accepts

A target name is <architecture>_<operating-system> and, optionally, _<environment>. The architecture field may name a sub-architecture instead of the bare architecture — rv64gc, armv7a-neon, aarch64v8.2, ppc64le-power9. The environment field is described under Environments; left out, each architecture and operating system pair declares its own.

A target name passes three checks, in order. The parser reads the name and fails on anything it does not know. The driver then refuses any name that is not in its own list of target names, which is the list printed under Supported values. A name that passes both goes to a backend, and the backend either lowers it or refuses it by name. Every row below was produced by running the release compiler with --target on a one-function program. Where a name is not in a row, it was not run.

Each row has one of these states. Supported and Partial rows link to a full entry above where one exists. Accepted, unverified means the compiler writes an artifact but nothing here shows that the artifact works. Accepted, not implemented means the name is accepted and the compilation stops with the refusal shown. Rejected on purpose and Nightly only are described under their own headings. Evidence is stated with the same terms as How to read this list.

Rejected on purpose

A name is refused here when accepting it would mean emitting something other than what it says. Each refusal carries a hint naming the spelling to use instead, so the message is the documentation.

ppc64-elfv1, powerpc64-elfv1Big-endian POWER here is ELFv2. ELFv1 calls through .opd function descriptors and is a different ABI, not a byte order. The hint names ppc64.

mips, mipsel, mips32, mips32elThe N64 ABI is implemented on 64-bit MIPS only, not O32. The hint names mips64 and mips64el.

s39064-bit z/Architecture only. The hint names s390x.

openbsd, netbsd, dragonflyThere is no syscall table, dynamic linker path or ELF brand for any of them. FreeBSD is the BSD that is implemented, and the hint names it.

ppc64 is no longer refused. It names the big-endian POWER target, which has a backend; see the names table above.

Nightly only

Three architectures and one operating system parse only in a build with the nightly Cargo feature. In a default build each is Unknown architecture or Unknown operating system. None of them is an available target, and none appears in the tables above.

arx64An experimental 64-bit architecture of this project's own. There is no silicon for it and there is no assembler for it, neither ras nor GNU. Code generation writes assembly text and nothing consumes that text. It is not a chip you can target.

riscv128128-bit RISC-V, which is itself a draft. The target carries a 128-bit pointer width so the rest of the compiler has to state what it does with one; that is what it is for. Code generation for it refuses by name rather than panicking, which is the behaviour the width was added to force. In a default build the name is Unknown architecture and an rv128 ISA string is no backend for that RISC-V width.

lisaParses behind the feature and is in no driver list, so --target lisa_linux is refused even on a nightly build.

arteryAn operating-system name for the Artery kernel. It parses and nothing else is wired to it.

An identifier that parses on a nightly build and not on a default build is not a supported target. Anything behind the feature may change or disappear without notice.

Environments

The environment is the fourth axis of a target, beside the architecture, the operating system and the sub-architecture. It is what decides the C library, the ELF interpreter, the C runtime startup objects and the compiler runtime, so s390x_linux states that it means glibc rather than inheriting that from whichever cross compiler the build machine happens to have. Six values exist and each architecture declares which of them it accepts.

gnuglibc, with the architecture's own floating-point ABI. The default for a hosted target on x86_64, aarch64, i686, riscv32, riscv64, ppc64le, ppc64, mips64, mips64el, loongarch64 and s390x.

muslmusl libc, accepted by the same eleven architectures. x86_64_linux_musl and s390x_linux_musl are target names. Read the caveat below before relying on one.

laminaLamina’s own C library. Accepted on x86_64 and aarch64; nothing else parses it. Nothing implements it. The axis carries the choice so the target grammar is settled, and the link refuses by name rather than borrowing another libc’s loader and start-up objects. It is a declared target, not a feature.

eabiARM EABI, soft-float calling convention. The default on thumbv6m and thumbv7m, and accepted on armv7.

eabihfARM EABI with floats in VFP registers. The default on armv7; not accepted on Cortex-M.

noneFreestanding: no libc, no startup objects, no compiler runtime. Every architecture accepts it, and it is the default wherever the operating system supplies its own runtime or there is none to supply — Darwin, Windows, WASI and the GPU targets.

A combination an architecture does not accept is refused by name before anything is compiled, and the refusal lists what that architecture does take:

$ lamina app.lamina --target x86_64_linux_eabihf
Error: Unsupported target 'x86_64_linux_eabihf': Environment 'eabihf' is not supported for x86_64
  Hint: x86_64 accepts gnu, musl, lamina, none

Naming lamina compiles and assembles and then stops at the link, which says what is missing and which environments do link:

$ lamina app.lamina --target x86_64_linux_lamina -o app
Error: cannot link x86_64_linux_lamina: cannot link against the lamina C library: the Lamina C library is
not implemented yet: there is no Lamina libc to link, no start-up objects and no dynamic loader for it;
write `x86_64_linux` for the environment this target declares, `x86_64_linux_musl` for musl, or
`x86_64_linux_none` for a freestanding binary

A few sub-architecture spellings imply an environment, because the spelling is the whole reason to write them: armv7a-sf and armv7r both mean eabi.

musl is declared, not yet demonstrated

The target model carries the musl interpreter and toolchain triple for each architecture that accepts musl, and the GNU link path refuses cleanly without a musl cross compiler: no musl gcc is installed for X86_64 (looked for x86_64-linux-musl-gcc). The default weld path does not pass the declared interpreter and weld writes its own, so an x86_64_linux_musl build on a glibc host produces an ELF whose interpreter is the glibc one. No musl binary has been built and run here.

Where the parser and the driver differ

The parser accepts more names than the driver. A name the parser accepts and the driver does not list is refused with Unsupported target and no reason. The reason is shown only when the parser itself fails, so x86_64_freebsd gets no explanation at all. Library code that calls the parser directly gets the wider set. The driver's list is the set that works from the command line. lamina --help names no targets in full. Its sub-architecture line gives examples, and the parser also accepts aarch64v8.1, armv7m, armv7a-sf and ppc64le-power10.

Semantics that do not vary by target

The things that usually differ quietly between architectures were checked against each backend and match. A frontend can rely on these without a per-target branch, which is the point of writing them down. Each is a clause of the IR semantics, which states the whole of what the IR means and says which clauses were run rather than read.

Overflowadd, sub and mul wrap on every target. One evaluator, IntBinOp::evaluate, serves the interpreter and the constant folder, so a folded constant and a computed value agree.

Shift countsA count computed at run time is masked to the operand width on every backend rather than left to the ISA, which disagrees about wide counts. Measured on x86_64: a runtime count of 33 on an i32 shifts by 1. A constant count outside the width is not masked, because a constant is something the author wrote: it is a compile error naming the range, shl.i64 shifts by 64, which is out of range for a 64-bit operand.

Division by zeroTraps everywhere, as does MIN / -1. x86_64 lets idivq raise it and adds an explicit guard for the narrow MIN / -1 case; aarch64 emits cbnz … udf #0; riscv emits bnez … .word 0; ppc64, armv7 and loongarch64 share the same check. Measured on x86_64: a program dividing by a runtime zero exits 136, which is SIGFPE.

i128 divisionGuarded in the shared wide lowering, so the guard is the same on every backend: both halves of the divisor are ORed to detect zero, and the signed MIN / -1 case is caught by comparing both words.

Float to integerTruncates toward zero, saturates to the target range, and turns NaN into zero — on x86_64, aarch64, riscv64 and ppc64 alike, and matching the interpreter. This is the classic silent cross-architecture divergence and it does not exist here. i686 would differ if it used x87, which reports an out-of-range or NaN operand as the integer indefinite, so it calls __fixdfdi instead and gets the contract’s answer.

Atomic orderingAll five orderings are carried from the IR through MIR to the backend one for one, and aarch64, riscv64 and ppc64 each consult the ordering per operation. A backend that cannot do atomics refuses the module; none of them silently drops to a weaker ordering.

Compare-exchange orderingsA failing atomic_cmpxchg performs the load and nothing else, so its failure ordering carries no release and may not order more than the success ordering does. Both rules are checked once, where the instruction is parsed, so every backend gets the same answer: atomic_cmpxchg cannot use seqcst failure ordering with relaxed success ordering. They used to be checked on some lowering paths and not others.

Atomic alignmentAn atomic access must be naturally aligned. Where the address is a base with a constant displacement, or a base with an index and a scale, that is decidable and it is decided: an address that cannot be aligned is refused by name before any backend sees it. An address the compiler cannot reason about is the program’s responsibility.

Optimizer and atomicsNo pass reorders, deletes or CSEs an atomic or a volatile access. Dead-code elimination treats every atomic and fence as side-effecting, memory forwarding clears its tables at any atomic or fence, CSE matches only arithmetic and comparison, LICM lists atomics as side-effecting, and both mem2reg and SROA refuse a slot an atomic touches.

Target by target

The same six questions for each target, so they can be read side by side. ABI is what a frontend must match. Lowers and Refuses are what the backend does with the IR; a refusal names the function and stops, which is the behaviour to prefer over a wrong ABI. Toolchain is what assembles and links it. Evidence says how the rest of the entry is known, and nothing is called tested without saying by what.

x86_64_linux

The reference. Every other backend is written against behaviour first established here, which is why a feature missing elsewhere is almost always "not yet written for that backend" rather than "impossible there" — the IR does not have target-conditional semantics. It is also the only target where a program that uses the C library goes from .lamina to a running binary without a tool Lamina did not write.

ABISystem V AMD64. Integer and pointer arguments in rdi rsi rdx rcx r8 r9, then the stack; floating point in xmm0–xmm7. Integer results in rax, with rdx for a second eightbyte; float results in xmm0. An integer aggregate up to 16 bytes travels in up to two integer registers; one larger than that is copied into the caller's argument area, and a large result is written through a hidden pointer the caller supplies. Callee-saved: rbx rbp r12 r13 r14 r15. Frames are rounded to a multiple of 16, so rsp is 16-byte aligned at every call.

LowersInteger and float scalars, integer aggregates by value, atomics including atomic_cmpxchg and fences, bit intrinsics, 128-bit vectors from the text IR, variadic calls, variadic definitions, inline assembly, i128, indirect calls, float-to-int and int-to-float in both signednesses.

RefusesAn aggregate with a float field, which no target accepts yet: aggregate not yet supported: %p of @sum has a float field; only integer aggregates cross a boundary so far. The refusal is raised in MIR lowering, before any backend sees it, which is why it reads the same everywhere. Under --sandbox, a function of more than one block: x86_64 JIT encoder currently supports only single-block functions.

Toolchainras assembles and weld links, with no host tool involved. This is the only target where that holds for a program that uses the C library.

EvidenceRun natively on this machine: compiled, assembled, linked and executed, with output and exit status checked.

DefectsNone recorded. -g produces real source lines: a hello-world build carries .debug_line through ras and weld, and the decoded table maps addresses to the right lines of the .lamina file.

x86_64_windows

The same instruction selection as x86_64_linux with a different calling convention bolted to it, so the arithmetic, atomics and aggregate handling are the Linux target's and need no separate trust. What differs is argument placement and, as a consequence, variadic functions: the variadic implementation is built around the System V register save area, where a callee spills its six integer and eight vector argument registers into a known 176-byte block and va_list walks it. Win64 has no such block — it spills into the caller's shadow space instead — so the backend refuses va_start rather than reuse a layout that does not describe the machine.

ABIWin64. Integer arguments in rcx rdx r8 r9, floating point in xmm0–xmm3, and the two banks share one positional slot each — a double in the second parameter position travels in xmm1 whatever came first. Aggregates of 1, 2, 4 or 8 bytes go by value and everything else by reference. The hidden return pointer takes rcx and pushes the other arguments one slot along. Callers reserve 32 bytes of shadow space. 16-byte aligned at the call.

LowersThe same scalar, aggregate, atomic, bit-intrinsic, i128 and indirect-call set as the Linux target, plus variadic calls.

aarch64_linux

The most complete cross target: everything a program normally needs lowers, and the two refusals are features rather than correctness gaps. The one thing to be careful of is argument alignment. ppc64le_linux and ppc64_linux

Both byte orders, one backend. ppc64le is little-endian and ppc64 is big-endian; both are ELFv2, and the endianness is a target property the lowering reads, not a separate code path. s390x_linux

The first big-endian target, which is what it was added for: everything that had quietly assumed little-endian byte order had to state its answer before this backend could emit anything. It is also the only cross target that goes all the way to a checked run here, because it is the only one whose cross C library is installed. It has no register allocator. Every virtual register lives in a frame slot and operands are shuttled through a fixed handful of scratch registers, so the code is large and slow and obviously correct in a way that a half-written allocator would not be. Asking for a global allocator is refused rather than ignored. Linux is the only operating system it accepts.

Two things to match from a frontend. The backend emits popcnt, which is a z196 instruction, and it emits it for population count and for trailing-zero count, so the output needs z196 or later whatever else the program does. And its va_list is the 32-byte block the s390x ELF ABI defines — long __gpr, __fpr; void *__overflow_arg_area, *__reg_save_area; — rather than a shape Lamina picked, so a Lamina va_list is the one a C function on this target expects.

ABIz/Architecture ELF, big-endian, 64-bit pointers. Integer and pointer arguments in %r2–%r6, floating point in %f0, %f2, %f4, %f6, then the stack. Integer results in %r2, float results in %f0. Every frame carries a 160-byte register save area at the bottom, which the prologue fills with stmg %r6,%r15. %r11 is the frame pointer and %r15 the stack pointer; %r0 is never used, because it reads as zero in an address. The stack is 8-byte aligned at a call, not 16.

LowersInteger and float scalars, integer aggregates by value, indirect calls, variadic calls, variadic definitions, atomics and fences, bit intrinsics (popcount, ctlz, cttz, bswap), integer rotates, checked arithmetic, thread-local storage, float-to-int and int-to-float. Division uses the even-odd register pair the hardware requires. POPCNT counts each byte on its own, so the byte counts are summed with a multiply; FLOGR gives the leading-zero count and LRVGR the byte reversal.

RefusesVectors: s390x vector operations — nothing implements the z13 vector facility. Float aggregates, as everywhere. Any register allocator but the incremental one, and any operating system but Linux, each by name.

ToolchainNeither half is Lamina’s. ras has no z/Architecture encoder, so assembly goes to GNU s390x-linux-gnu-as; weld does not link s390x, so the link goes to s390x-linux-gnu-ld with -m elf64_s390 and /lib/ld64.so.1 as the interpreter. The start-up objects come from s390x-linux-gnu-gcc, not from the host compiler. That distinction used to be wrong and it is the reason this target did not work: a cross link got no crt1.o at all, so -e _start resolved to nothing, the linker fell back to the first function in .text, and the program never reached __libc_start_main or exit. It now links the target’s own start-up objects, and a cross gcc that cannot be found is an error naming the missing file rather than a binary that runs wrong.

EvidenceCompiled, assembled, linked and run. The recorded programs are built for s390x and executed under qemu user-mode emulation against the cross glibc, and their output is diffed against the expected one. Inline assembly is among what runs. A recorded program is skipped only where the reason is written down against it: inline_asm_rdtsc reads the x86 timestamp counter, which has no z equivalent, and vector_operations needs the z13 vector facility. That is a real run of the generated code and not a run on z hardware; an effect that only shows on a real machine would not be caught. The ABI is also covered by unit tests over argument classification, frame sizes and call areas.

DefectsNone recorded. The i128 helpers are no longer a gap: the driver compiles Lamina’s own builtins/ for s390x and names the objects on the link line, and the cross libgcc.a goes on after them where one is found.

armv7_linux

A 32-bit target with a 64-bit integer problem and a hard-float ABI, and the two interact. Because armv7 has no 64-bit registers, an i64 is legalized into a pair of 32-bit ones, and MIR models that pair as an eight-byte integer aggregate. That representation is why its one known defect exists: at a return, the backend cannot tell a legalized i64 from a real eight-byte struct, and AAPCS wants opposite things for them — registers for the integer, memory for the composite. It chooses registers, on the stated grounds that getting a 64-bit integer wrong would be the costlier mistake, and a five-to-eight-byte struct pays for it. The floating-point side is the other thing to match carefully: floats live in a bank of their own and never touch r0–r3, except when the call is variadic, where the base standard applies instead and a double travels in core registers after all.

ABIARM state, AAPCS in the VFP hard-float variant. Core arguments take r0–r3 and then the stack; floating point takes s0–s15 and d0–d7 from a bank of its own, back-filled. Once one co-processor argument misses the bank the rest of the bank is closed and later floats go to the stack, never into core registers. A variadic argument is placed by the base standard, so a double handed to printf travels in an even core pair or on the stack. An argument of 8-byte alignment rounds the core register number up to an even one — the rounding AArch64 and RISC-V are missing. A result of up to two words comes back in r0:r1; anything larger through a buffer whose address arrives as a hidden first argument in r0. Callee-saved: r4–r11 and d8–d15. The prologue masks sp with bic sp, sp, #15, so it is 16-byte aligned. Needs a Cortex-A7 or later, because it uses hardware sdiv and udiv rather than calling a division helper for 32-bit operands.

LowersInteger and float scalars, integer aggregates by value, indirect calls, variadic calls, bit intrinsics, float-to-int and int-to-float, 64-bit integers legalized into register pairs with __divdi3 and __udivdi3 from the C library for division.

RefusesAtomics: armv7 backend does not implement atomic operations, and for a 64-bit one the refusal comes earlier, from the pair legalizer, with the reason: an atomic operation on a 64-bit integer on a 32-bit target: two words cannot be read or written atomically without a double-word atomic. Inline assembly, which stops in MIR lowering as an unsupported instruction. The va_* family in a definition. i128: names a 128-bit integer on a 32-bit target: that takes four registers, and only pairs are split. An indirect call whose argument or result is 16 bytes wide: an indirect call carries no callee signature to pass a 16-byte aggregate by, so call the function directly — the classification needs a declared parameter type and a function pointer does not carry one. Float aggregates.

Toolchainras has no armv7 encoder and no cross assembler is installed here: ras cannot assemble Armv7 Linux; no GNU as is installed for Armv7 (looked for arm-linux-gnueabihf-as). With that assembler present it would fall through to it, then to GNU ld.

EvidenceCompiled only, not executed. Assembly text is produced and read; nothing assembles, links or runs it here, including under qemu. The ABI description comes from the placement code and from reading the emitted prologues, where the register and VFP assignments are visible directly.

DefectsA composite of 5 to 8 bytes is returned in r0:r1 where AAPCS says memory, so a C caller of such a function reads the wrong value. This is the deliberate trade described above, not an oversight, and it will stay until MIR can distinguish a legalized integer pair from a genuine composite.

thumbv6m and thumbv7m

Cortex-M, bare-metal ELF, Thumb only. There is no ARM state on a Cortex-M, so the choice the armv7 backend made — A32, where every data-processing instruction is conditional and a boolean needs no IT block — is not available here. The only conditional data-processing instructions this backend emits are a conditional set and a conditional move, and on ARMv7-M each writes the IT and the one instruction it guards together, so the block is always one instruction long and its pattern always matches. ARMv6-M has no IT at all, and there the same two helpers branch over one instruction instead. No other IT is emitted anywhere.

The frame is addressed from the stack pointer, which the prologue sets once and nothing moves afterwards; the widest outgoing argument area any call needs is reserved there too. That is what makes ARMv6-M workable, where a load against a general register reaches 124 bytes but one against the stack pointer reaches 1020.

ABIAAPCS, soft float, 32-bit pointers, 8-byte stack alignment at a call. The two targets differ by instruction set: thumbv6m is ARMv6-M, Thumb-1, a Cortex-M0 or M0+; thumbv7m is ARMv7-M, Thumb-2, a Cortex-M3, M4 or M7. armv6m and cortex-m0 are spellings of the first; armv7m and cortex-m3 of the second.

LowersInteger scalars up to 32 bits, control flow, direct and indirect calls, recursion, integer aggregates by value.

RefusesFloating point, by name and with the reason: the M0 has no FPU, and the single-precision VFP an M4F or M7 may carry is not used here, so the message is does not implement floating point rather than a soft-float libcall to a library nothing ships. A hard-float variant spelling is refused for the same reason. 64-bit integers, until the legalization pass splits them into register pairs for this backend. Atomics, vectors, inline assembly and variadic definitions. An access whose declared alignment is narrower than its type, on both: ARMv6-M takes a HardFault on an unaligned access outright, and ARMv7-M takes a UsageFault on one whenever CCR.UNALIGN_TRP is set, which this backend cannot establish is clear because it emits no startup code and whatever does may write the field. Neither is lowered to a byte-at-a-time sequence, which this backend does not emit. On ARMv6-M additionally: integer division, which the instruction set does not have. A function named like a Thumb register is refused, because bl r0 reads as an instruction rather than a symbol.

ToolchainAssembly text only. ras has no Thumb encoder, and the Cortex-M toolchain is arm-none-eabi, which is not a GNU Linux triple, so the driver has no cross assembler to fall back to either. Both _unknown and _linux are accepted and produce bare-metal ELF assembly; no other operating system is.

EvidenceCompiled only. The assembly has been read; nothing here assembles, links or runs it.

i686_linux

The 32-bit x86 target. A 64-bit integer comes back in %edx:%eax, which is what the i386 convention asks for, and 64-bit division, remainder and float conversion go to the compiler runtime — __divdi3, __udivdi3, __fixdfdi and the rest, which the driver compiles for the target and puts on the link line. Nothing from the host libgcc is wanted for them. The conversion answers what the contract names rather than what x87 would: the routine saturates and maps NaN to zero, so i686 agrees with every other backend instead of returning the x87 integer indefinite. Narrow signed division traps where it overflows, so div.i8 -128, -1 faults rather than answering −128, which is what it used to do and what no other backend did. Note also that no callee-saved register is ever touched: every virtual register lives in a frame slot and values move through %eax, %ecx and %edx, which is what six general registers afford.

ABIcdecl, which is 32-bit System V. Every argument goes on the stack, each rounded up to a four-byte word, and the caller cleans up — with one exception: a callee that returns through a hidden struct pointer releases that pointer itself with ret $4, which is what the i386 convention asks of it. Integer results in eax, a 64-bit result in edx:eax, floating point on the x87 stack. Callee-saved: ebx esi edi ebp, none of which the backend uses. The stack is 16-byte aligned at the call: call pushes four bytes onto an aligned esp and the prologue pushes ebp, leaving it eight past a boundary, so the frame is sized to 8 mod 16 to put it back on one.

Lowers32-bit integer and float scalars, a 64-bit integer return in %edx:%eax, 64-bit division, remainder and float-to-integer conversion through the compiler runtime, control flow, direct calls, indirect calls, variadic calls, bit intrinsics.

RefusesAtomics: i686 atomic operations and fences are not implemented. Inline assembly. A variadic definition. i128, through the four-register message. An indirect call carrying a 16-byte aggregate. Float aggregates.

ToolchainNeither half is Lamina's: [WARN] ras cannot assemble I686 Linux; assembling with GNU as instead, then [WARN] weld cannot link I686 Linux yet; linking with GNU ld instead. Both tools are the host's own binutils, driven with --32 and -m elf_i386, so no cross toolchain is needed on an x86_64 machine.

EvidenceRun here: compiled, assembled, linked and executed. The binary is a 32-bit ELF and runs on this x86_64 host through 32-bit compatibility, printing correctly and returning the right exit status. It is a real run, but not a run of Lamina's own toolchain and not on a 32-bit machine.

Defects-g numbers instructions instead of emitting source lines. x86_64 emits .loc 1 3 5 for the statement the instruction came from; i686 emits .loc 1 1 0, .loc 1 2 0, .loc 1 3 0 and so on, counting upward with no relation to the .lamina file. A debugger will step through it, but the lines it shows are fiction.

riscv32_linux and riscv32_unknown

These two spellings are not variants of the same thing, and confusing them wastes an afternoon. The backend is shared; what differs is whether a C library exists, which decides what happens the moment a program divides a 64-bit integer.

ABIILP32D in shape. Integer and pointer arguments in a0–a7, floating point in fa0–fa7, results in a0 and fa0, sp 16-byte aligned. A 64-bit integer is legalized into a pair of 32-bit registers.

Lowers32-bit integer and float scalars, integer aggregates by value, 32-bit atomics, control flow, direct calls, 64-bit integers as register pairs.

The differenceDivision of a 64-bit integer needs __divdi3 or __udivdi3. On riscv32_linux those come from the C library and the backend emits the call. On riscv32_unknown there is no C library, and rather than emit a call that cannot link, the compiler refuses: `__udivdi3` is a compiler runtime helper that a target without a C library does not provide; define it in the module, or name an implementation with LAMINA_BUILTINS=__udivdi3=<symbol>. The refusal names the way out, and it is the same mechanism for any runtime helper. A great many programs divide somewhere, so on the freestanding spelling that refusal surfaces far more often than its narrow wording suggests.

RefusesBoth spellings refuse: i128, through names a 128-bit integer on a 32-bit target: that takes four registers, and only pairs are split. 64-bit atomics: an atomic operation on a 64-bit integer on a 32-bit target: two words cannot be read or written atomically without a double-word atomic. va_arg of an i64: a variadic slot holds one word, and reading the pair is not implemented. A variadic argument wider than one word, named at the call site: a variadic i64 argument to @printf spans two rv32imafd registers, which this backend does not yet place, and the same for an f64. Bit intrinsics: RISC-V32 backend does not support integer bit intrinsics yet. Float-to-int: RV32 float to integer conversion is not supported. Indirect calls: Riscv32 does not yet call through a pointer, as @main does. Inline assembly. Float aggregates.

Toolchainras writes an ELF32 object for riscv32 now, so riscv32_linux gets past the assembler. It stops at the link: weld does not link riscv32 and no riscv32-linux-gnu-ld is installed. riscv32_unknown stops one stage earlier, because ras writes objects for Linux and the BSDs and not for the unknown operating system. There is no end-to-end rv32 path today.

EvidenceCompiled on both spellings, and assembled to an ELF32 object on riscv32_linux. Nothing linked or run.

DefectsNone recorded separately from the refusals above. For 64-bit work on RISC-V, use riscv64_unknown.

wasm32 and wasm64

WebAssembly is the one target with no calling convention to match, because it has no registers: a function's signature is its ABI, and locals live in the module's own locals plus a shadow stack in a mutable global. The pairing of widths catches people out. wasm32 has 32-bit pointers and wasm64 64-bit, but both have native 64-bit integers, so a 32-bit pointer does not imply 32-bit arithmetic and an i64 needs no legalization on either. That same design is behind the defect below: the backend holds every integer value as a wasm i64 internally — constants, arithmetic, results — and the declared signature of an imported function is generated from that internal view rather than from the IR type. Aggregates are refused for a different reason: with no registers there is no classification to apply, so passing a struct by value would mean inventing a memory and copy convention, and that decision has not been made.

ABIThe function's wasm signature. Locals live in the module's locals and a shadow stack held in a mutable global $sp that starts at the end of the first page. wasm64 declares a memory64 memory and indexes it with i64. There is no aggregate rule, because aggregates do not cross a boundary by value. Three spellings exist: wasm32_wasi, wasm32_unknown and wasm64_unknown; there is no wasm64_wasi.

LowersInteger and float scalars including i64 on both widths, control flow, direct calls, indirect calls through a function table where a function address is its table index, variadic calls, float-to-int and int-to-float, 128-bit vectors on simd128. wasm32_wasi writes its own digits, prints through fd_write and exports _start. The freestanding spellings import env.writebyte from the host instead, so a plain wasm runtime cannot run them alone — the host has to supply that import.

RefusesAggregates by value, naming the function and the width: Wasm32 does not yet pass aggregates by value, as @make_pair does, and the same for Wasm64. Atomics, naming the instruction: WASM backend: instruction not yet supported: atomic_store.i32 1, [[v0]] seqcst. Bit intrinsics: WASM backend does not support integer bit intrinsics yet. Variadic definitions: WASM backend does not support variadic arguments yet. Inline assembly: inline assembly is not supported by the WASM backend; it is x86_64 Linux only. On the freestanding spellings, a runtime helper such as __divti3, through the same no-C-library refusal rv32 gives.

ToolchainThe backend emits WAT text, which wat2wasm then assembles. That tool is not on this machine, so a build here stops at Failed to spawn wat2wasm and only --emit-asm completes. Neither ras nor weld is involved; there is nothing for them to do.

EvidenceCompiled only, not executed: WAT is produced and read, and nothing assembled it to a .wasm or ran it under a wasm runtime. The defect below was found by reading the emitted module's import section against the IR it came from.

DefectsAn imported function's integer parameters and results are declared i64 whatever the IR said. fn @f(i32 %a) -> i32 declared @extern is imported as (func $f (param i64) (result i64)), and a function declared to return i32 is defined with (result i64). A host that exports the function the IR describes will not instantiate the module. Pointer parameters are not affected and come out correctly: on wasm32 a ptr parameter is declared (param i32) and on wasm64 (param i64), which is right for each.

nvptx64_cuda and amdgcn_amdhsa

These are not binary targets and should not be read as unfinished versions of one. A GPU backend emits text for a GPU toolchain to take further, so there is no linker step to be missing and no C ABI to match. The two refusals that stop most programs follow from the execution model rather than from unwritten code: a module with no @kernel has no entry point a device can launch, and globals have no meaning until a memory space is chosen for them — which is also why a program that merely prints a string is refused, since the string is a global.

ABINo C calling convention to match. PTX declares kernel parameters in a parameter space — .visible .entry add(.param .u64 .ptr .global .align 1 arg0) — and AMDGPU emits an HSA kernel with its own metadata. There are no argument registers, no callee-saved set and no stack alignment rule for a frontend to honour. --mcpu selects the AMDGPU processor, gfx900 or gfx1200.

LowersInteger arithmetic, memory operations, control flow and threading, inside a function marked @kernel.

RefusesA module with no kernel, before anything else: GPU code emission: functions must be marked as kernels. Globals: PTX does not yet support global variables and AMDGPU does not yet support global variables, which rules out most programs written for the other targets. Aggregates by value, naming the function. Atomics. Inline assembly.

ToolchainNeither ras nor weld, and no linker. The output is a text artifact — a .ptx file for NVIDIA, a .s file for AMD — that a GPU toolchain takes from there. There is no linked binary to produce and none is attempted.

EvidenceCompiled only, not executed. A kernel compiles and the PTX was read; nothing was assembled by a GPU toolchain and nothing was run on a device.

DefectsNone recorded. The missing global-variable support is the limit worth planning around.

What each backend can lower

Integer scalars, control flow, direct callseverywhereThe common path. Every published backend lowers it, including both wasm widths and, inside a kernel, the GPU backends.

On i686, armv7 and rv32 they are split into register pairs, with __divdi3/__udivdi3 for division; i686 returns one in %edx:%eax. Vectors, 256-bitnowhere<8 x i32> parses and validates, and every backend then refuses it. Vectors across a callnowhereA vector type may be an instruction suffix and the type of a value. It may not be a parameter, a return type, a struct field, a global or a stackalloc, and IR validation refuses each by name. A helper that works on vectors takes a pointer. Nobody has written the per-target vector calling convention down.

The 32-bit targets refuse it: four registers, and only pairs are split. loongarch64 and WebAssembly refuse it as a 16-byte aggregate. On aarch64 and riscv64 it is also the type that exposes the argument-alignment defect.
Calling a variadic functionx86_64 aarch64 riscv64 ppc64le loongarch64 armv7 i686 wasmWorks nearly everywhere, because a call site only has to place the arguments. rv32 refuses an argument wider than one word, naming the callee.
Defining a variadic functionx86_64 Linux (System V), s390xHarder than calling one: the callee has to spill its argument registers into a save area and va_list has to walk it, and that layout is per-ABI. Two are written. s390x uses Lamina's own 24-byte va_list rather than the 32-byte one its ELF ABI defines, so its va_list does not cross into C. Every other target refuses, each naming itself; Win64 among them.
Inline assemblyx86_64 Linux, s390xAn asm operand is bound to a physical register before the template runs, from a pool the backend owns, so each register file needs its own wiring. x86_64 and s390x have it; s390x refuses %r9, %r11 and %r15 as operands or clobbers, because those carry the frame. A template is assembly text, so one written for x86_64 does not assemble for s390x. Other targets refuse the module; AArch64, RISC-V, PowerPC64, LoongArch64 and WebAssembly each name themselves, and on the 32-bit targets it stops earlier, in MIR lowering, as an unsupported instruction.
Float to integerx86_64 aarch64 riscv64 ppc64le loongarch64 armv7 i686 rv32 wasmSaturating, NaN to zero, identical on every backend that has it. i686 and rv32 get it from the compiler runtime rather than from an instruction, which is why they now have it and why a freestanding 32-bit target does not.
Source-line debug infox86_64-g emits .file/.loc and ras writes minimal ELF DWARF. On x86_64 the decoded line table matches the .lamina source. On i686 the line numbers are an instruction count.
JIT into executable memoryx86_64, default CLI buildThe in-memory encoder handles single-block functions. --sandbox refuses a multi-block one by name: x86_64 JIT encoder currently supports only single-block functions; 'main' has 4 block(s). Plain --jit falls back to an executable written under the cache directory and runs it correctly. The two paths agree on the compiler runtime symbols now, but the shipped routines are not encoded in memory, so --jit on a program that reaches a 128-bit helper always takes that fallback and is an ahead-of-time build with an extra step. The JIT also refuses some return types that the ahead-of-time path accepts.

How to read this list

Target parsing, code generation, assembly, and linking are separate stages. A recognized identifier does not promise an end-to-end compiler path.

Driver acceptanceThe parser recognizes more names than the driver accepts, and the driver accepts more names than this matrix describes. Many operating-system names are accepted and change nothing; Names the compiler accepts says which. Recognition alone is not a support claim.

What the evidence row meansFour phrases appear above and they are not interchangeable. Run natively: compiled, linked and executed on this machine, with output and exit status checked — x86_64_linux, and i686_linux through 32-bit compatibility on the same host. Assembled: a real assembler accepted every instruction the backend emitted, which is weaker than a run but catches a malformed operand or relocation — ppc64le, and the ras-assembled cross targets. Compiled only, not executed: assembly text was produced and read and nothing else touched it. Not exercised: nothing at all. One target is run under emulation: s390x, whose recorded programs are built and run under qemu user-mode against the cross glibc with their output checked. It is the only cross target with a cross C library installed. Qemu user-mode emulation is there for the rest; what is missing is their libraries, so those programs never link far enough to hand it anything.

Toolchain fallback is announcedWhen ras or weld cannot handle a target, the driver says so on stderr with a [WARN] and uses the GNU tool named in that message. It never falls back silently. If no suitable host tool is installed, the build stops with an error naming the tool it looked for. -c gnu, -c clang and --assembler override the choice explicitly.

Where weld and ras standweld links x86_64 on Linux, Windows and macOS, aarch64 on macOS, and riscv64 for a program that needs no C library symbol. ras encodes x86_64, aarch64, riscv32, riscv64 and little-endian ppc64le; it writes ELF for all of them, COFF for x86_64 only and Mach-O for x86_64 and aarch64. Big-endian ppc64, s390x, mips64, LoongArch64, armv7, Cortex-M, i686, WebAssembly and the GPU targets go elsewhere. The pairing that is Lamina's own end to end, for a program that uses libc, is x86_64 Linux.

Experimental register allocationGlobal linear-scan and graph-color allocation are not available for every backend. The default allocator remains the practical choice.

Nightly identifiersA few architectures exist only behind the nightly feature and are not described here. An identifier that parses on a nightly build and not on a release build is not a supported target.
