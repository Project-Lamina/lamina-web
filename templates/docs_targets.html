Targets and backends

What a target supports is a list of features, not a score. x86_64 and AArch64 do all of it. RISC-V 64 and PowerPC64 do all of it except aggregates by value, which they refuse rather than lower to a guessed ABI. The rest emit text nobody has run.

Executed targets

Compiled, run and diffed against recorded output. First three on a CI job on that operating system, last three under qemu by hand.

TargetStatusNotes

x86_64_linuxTestedReference path. Everything lands here first. SysV: integer aggregates up to 16 bytes in registers, bigger ones in memory, return pointer in rdi.

x86_64_windowsTestedWin64 passes aggregates of 1, 2, 4 or 8 bytes by value and everything else by reference. Return pointer goes in rcx and pushes the other arguments along.

aarch64_macosTestedApple Silicon. AAPCS64: integer aggregates up to 16 bytes in registers, bigger ones returned through x8.

aarch64_linuxTestedSame ABI as macOS, cross-executed under qemu at -O0 through -O3, through the assembler. The direct binary encoder still misses IntConvert and Copy.

riscv64_unknownPartialScalars, control flow and callptr run. No aggregate ABI yet. RV64 only, riscv32_unknown has never been run.

ppc64_linuxPartialELFv2, same gap as RISC-V. Locals sit above the 64 byte parameter save area, because printf spills its register arguments there.

What each backend can lower

A backend refuses what it cannot classify. An aggregate it has no rule for is a compile error naming the function, never a silently wrong ABI.

FeatureWhere it worksNotes

Integer scalars, control flow, callseverywhereCommon path. Every published backend lowers it.

Integer aggregates by valuex86_64 aarch64A struct, tuple or array crossing a boundary by value. RISC-V, PowerPC64, WebAssembly and the GPU backends refuse the module instead of guessing a classification. A pointer to one is a scalar and works anywhere.

Float or mixed aggregatesnowhereA struct with a float field is refused everywhere, x86_64 included.

Calls through a pointerx86_64 aarch64 riscv64 powerpc64WebAssembly refuses callptr: nothing emits a function table yet.

Direct binary emissionx86_64 aarch64x86_64 is complete. AArch64 covers part of it and falls back to the assembler.

JIT into executable memoryx86_64Nightly feature. Calls and multi-block functions still need doing.

How to read this list

Target parsing, code generation, assembly, and linking are separate stages. A recognized identifier does not promise an end-to-end compiler path.

Driver acceptanceThe command-line parser recognizes more identifiers than this public matrix. Recognition alone is not a support claim.

AArch64 binary emissionThe direct encoder covers part of the instruction set. Assembly workflows do not go through it and are fully supported.

Experimental register allocationGlobal linear-scan and graph-color allocation are not available for every backend. The default allocator remains the practical choice.
