Calling conventions

A Lamina function has to agree with C on where arguments live, or nothing links. Each backend implements one platform ABI. Where a backend has no rule for something, it refuses the module and names the function instead of guessing.

How this page was checked

The register lists and the aggregate rules were checked against the backend source, and the aggregate and variadic behavior was checked by compiling and running test programs under qemu where a target allows it. In the most recent pass, the x86_64 aggregate and variadic programs were run natively and the s390x ones under qemu, with their output checked. No other cross target was run: their C libraries are not installed, so their programs do not link. The claims about what a C compiler does on each platform were not checked against C-generated code in this pass, and the Windows and macOS rules were not run here. CI runs the testcase suite on windows-latest and macos-latest (arm64), and it passes there.

What each backend implements

TargetConventionInteger and float banks
x86_64 Linux, macOSSystem V AMD64Integers in rdi rsi rdx rcx r8 r9, returned in rax and rdx. Floats in xmm0 upward, returned in xmm0.
x86_64 WindowsWin64Integers in rcx rdx r8 r9 with 32 bytes of shadow space. A hidden return pointer takes rcx and pushes the rest along.
aarch64AAPCS64Integers in x0–x7, floats in d0–d7. A hidden return pointer goes in x8, which is not an argument register.
riscv64LP64DIntegers in a0–a7, floats in fa0–fa7. A variadic float travels in the integer bank instead.
ppc64le, ppc64ELFv2Integers in r3–r10, floats in f1–f13. The caller reserves a 64 byte parameter save area and the callee may spill its register arguments into it, so the callee keeps its locals above it. Both byte orders use the same convention; only the endianness differs. Elsewhere on this page ppc64 means the backend, not one of the two.
s390xz/Architecture ELFIntegers in %r2–%r6, floats in %f0, %f2, %f4, %f6. Results in %r2 and %f0. Every frame opens with a 160-byte register save area. Big-endian, and the stack is 8-byte aligned at a call rather than 16.
mips64, mips64elN64Integers in $4–$11, floats in $f12–$f19, positionally alongside them: an argument takes the register matching its first doubleword whatever its class. Results in $2 and $f0. $25 carries the callee address, which is how a position-independent callee finds its own global pointer.
armv7AAPCS, VFP hard floatIntegers in r0–r3, floats in the VFP bank. A 64-bit value takes an even-odd register pair.
thumbv6m, thumbv7mAAPCS, soft floatIntegers in r0–r3. There is no float bank: floating point is refused rather than lowered to soft-float libcalls that nothing here ships.
i686cdeclEvery argument on the stack, caller-cleaned. Integer results in eax, and edx:eax for 64 bits, which is the pair this backend does not yet produce. Floats come back on the x87 stack.
wasm32 wasm64NoneScalar parameters and results only, as wasm value types.
amdgpu ptxKernel contractScalar kernel arguments. Not a C calling convention.

Aggregates

An aggregate here is a struct or array crossing a function boundary by value. A pointer to one is a scalar and works on every backend.

type !Pair = struct { a: i64, b: i64 }

fn @sum_pair(!Pair %p) -> i64 {
entry:
  %pa = getfieldptr.!Pair %p, 0
  %a = load.i64 %pa
  %pb = getfieldptr.!Pair %p, 1
  %b = load.i64 %pb
  %s = add.i64 %a, %b
  ret.i64 %s
}

fn @sum_ptr(ptr %p) -> i64 {
entry:
  %a = load.i64 %p
  ret.i64 %a
}

Classification differs per ABI, and there is no rule that is right everywhere. 32 bytes goes to memory on System V, AAPCS64 and LP64D, but stays in general registers on ELFv2. Two floats pack into one SSE register on System V and nowhere else. So each backend classifies for itself, and a backend without a classifier refuses rather than picking someone else's answer.

TargetBy valueRule
x86_64 System VYesUp to 16 bytes in consecutive integer registers, or on the stack when too few remain. Larger goes to memory, returned through the hidden pointer in rdi.
x86_64 Win64YesOnly sizes 1, 2, 4 and 8 travel by value. Every other size goes by reference, which is what Win64 requires rather than a shortcut.
aarch64YesUp to 16 bytes in x0–x7, or whole onto the stack when the remaining registers do not hold it. Larger arguments pass the address of a copy the caller makes. Larger returns go through the caller's buffer in x8.
riscv64YesUp to two doublewords in a0–a7. With one register left, the first doubleword takes it and the rest goes on the stack. Larger than two doublewords passes by reference, and a result that size returns through a hidden pointer in a0.
ppc64YesConsecutive doublewords in r3–r10. When the registers run short the rest spills into the parameter save area, splitting the aggregate rather than demoting it. A result over two doublewords returns through a hidden pointer in r3.
wasm amdgpu ptxNoRefused at lowering, naming the function: Wasm64 does not yet pass aggregates by value, as @make does.

Two limits apply on every target, x86_64 included. An aggregate crossing a boundary must have integer fields only, so a struct holding an f32 or f64 is refused everywhere. An empty aggregate is refused too.

What is missing

Float and mixed aggregatesRefused on every backend. System V packs two floats into one SSE register, AAPCS64 has homogeneous float aggregates, and ELFv2 splits a {long, double} across both banks. None of that is written yet.

Aggregates on wasm and the GPU backendsNot planned for the GPU kernel contract. wasm would need a layout decision first. Every other backend passes integer aggregates by value now.

Defining a variadic functionCalling one works on every backend in the table below. A variadic body (va_start and va_arg) is written on x86_64 System V, Win64, AArch64 Darwin and s390x. AArch64 Linux, riscv64 and ppc64 refuse va_start by name. So Lamina can call printf everywhere in that table, and can be printf on four targets.

valist is the platform'sThe size and alignment of valist are a property of the architecture, taken from the ABI that defines the struct field by field, not from the pointer width. x86_64 System V is 24 bytes (gp_offset, fp_offset, overflow_arg_area, reg_save_area); AAPCS64 is 32; the s390x ELF ABI is 32; i686 and 32-bit ARM are a 4-byte char *; riscv, ppc64 ELFv2, loongarch, mips n64 and wasm are one pointer. So a Lamina valist is the one a C function on that target expects. Where no ABI defines one — the GPU targets, arx64, riscv128 — the type is refused rather than given a made-up size. s390x used to get Lamina's own 24-byte block and did not cross into C; it now gets the ABI's.

Tail callscallptr works on x86_64, aarch64, riscv64, ppc64 and wasm. The IR has no tailcall instruction at all, direct or indirect; the parser rejects the spelling.

Vector call ABIVectors have arithmetic and memory operations on several backends, but no backend passes or returns one across a function boundary.

Calling a variadic function

A declaration says where the named parameters stop.

@extern
fn @printf(ptr %fmt, ...) -> i32

Each argument past them is promoted the way C promotes one: a float widens to f64, everything else travels as a word. Then each backend does what its ABI asks.

TargetWhat the call doesWhy
x86_64 System Val holds the vector countA variadic callee reads al to decide whether to spill the SSE registers.
x86_64 Win64Nothing extraWin64 passes a variadic float in both the SSE and the integer register, which the positional rule already does.
aarch64 DarwinStackApple puts every variadic argument in an eight-byte stack slot, whichever registers are free.
aarch64 LinuxRegistersAAPCS64 treats a variadic argument like a named one.
ppc64 ELFv2Float in both banksThe callee's va_arg may read either, so the bits go to the FPR and the positional GPR.
riscv64 LP64DFloat in integer bankLP64D sends a variadic float through a0–a7 as its bit pattern.

On x86_64, a callee with no declaration is treated as possibly variadic, and al is set.

Known gap: callptr. The IR accepts a bare ... in a callptr, but the x86_64 backend ignores it and does not set al. So a float argument passed through a pointer to a variadic function is not safe on x86_64 yet. Call the variadic function directly through an @extern declaration for that case. Found by reading the x86_64 backend. A simple test call still printed the right value, so the failure does not show in a small program.

Reading a refusal

An unsupported boundary is a compile error naming the value and the function, never a silently wrong ABI. The check runs at the start of every AOT backend and before JIT encoding, so it cannot be skipped by reaching for a per-architecture emitter directly.

$ lamina sum.lamina --target wasm32_wasi --emit-asm -o sum
Error: "Code generation failed: Codegen Error: Unsupported feature: Wasm32 does not yet pass aggregates by value, as @sum_pair does"
