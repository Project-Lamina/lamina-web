The toolchain today

Three repositories make up the toolchain: lamina (the compiler, with the C bindings in lamina-c/), lamina-ras, and lamina-weld. The C bindings have their own ABI version, which is set by the crate version.

ComponentLatest releaseRole
lamina{{#if lamina_version}}v{{lamina_version}}{{else}}—{{/if}}IR, MIR, optimizer, code generation, compiler driver.
lamina-ras{{#if ras_version}}v{{ras_version}}{{else}}—{{/if}}Assembler, an alternative to as/GAS. Assembly source to relocatable object.
lamina-weld{{#if weld_version}}v{{weld_version}}{{else}}—{{/if}}Linker, an alternative to ld/lld/mold. ELF, Mach-O, PE.
lamina-c{{#if lamina_version}}ABI {{lamina_version}}{{else}}—{{/if}}C bindings. Their ABI version is the crate version.

The release column is the newest tag on each repository. The working tree runs ahead of it.

Target support

Target names are the ones the driver accepts. A name the driver recognizes is not a support claim; Targets and backends has the full list and what each one does. The driver accepts eighteen architectures in a default build and all eighteen emit code; arm32 was the nineteenth and is now refused where the target string is parsed, with a hint naming armv7. The table below is the shorter question of which are finished.

What does not work

These are gaps a user can hit today. Milestone work is listed under Milestones; this table holds the rest.

0.1 — Correct on the targets we claim In progress

The targets that are done are the ones whose output is run and checked. The targets that are in progress compile, and their output is read or assembled and not run.

Correctness

Windows outputDone for x86_64 Windows. writebyte no longer falls through to a Linux syscall, the PE emitter resolves C runtime imports, and Windows links request a CRT. Win64 aggregate passing and the hidden return pointer in rcx are implemented.

RV64G from the RISC-V backendIn progress. Scalars, control flow, calls and aggregates by value are lowered. What is left is execution: nothing has run an RV64 binary, so the ABI is checked at the call boundary only.

PowerPC64 ELFv2In progress. Locals sit above the parameter save area, and aggregates by value are lowered. Not linked or run, for want of a cross toolchain.

Deterministic output on every backendIn progress. Fixed on x86_64 by ordering register sets. The other backends have not been audited for hash-ordered emission.

Language

External function declarationsDone. See Features above.

Toolchain

Split the toolchain flagsIn progress. --assembler chooses the assembler (ras, gas, clang). -c, or --compiler, chooses the toolchain (gnu, clang, msvc, lamina) or a linker alone (ld, lld, mold, weld, link, cl). There is no --linker flag. Unknown values are not rejected; see the gaps table.

Move driver work out of weldIn progress. The driver computes startup objects and the dynamic linker for its own GNU-style path. On the default ras and weld path, weld still supplies them, and it falls back to a hardcoded interpreter path when none is given. See the reasoning.

ras and weld as the default on x86_64 LinuxDone. See Features above.

Testing

Testcase suite on three platformsDone. The testcase suite (176 cases, run by run_tests.py) passes on ubuntu-latest, windows-latest and macos-latest (arm64) in CI.

Release and docs

First C bindings releaseDone. Stable and nightly C SDK archives are published, and the install page documents them.

One story everywhereNot started. The README describes the supported architectures as one list, without the done, in-progress and not-started split. The target table on this page is the reference.

0.2 — A backend you can add a target to In progress

Adding an architecture should mean implementing a trait, not editing a dozen match statements.

A codegen traitIn progress. A Codegen trait exists in the MIR code generator. Target selection is not yet driven by it, and adding a target has not been measured against the one-module bar.

Calling conventions in MIRNot started. Conventions are still written per backend.

AArch64 binary emissionIn progress. The assembly path works. The direct binary encoder still misses IntConvert and Copy.

ld command-line parity in weldIn progress. Accepted: -o, -e, -l, -L, -m, --dynamic-linker, -shared, -static, -nostdlib, --gc-sections, -z, -rpath, --Map, --start-group/--end-group, -r, --strip-all, --build-id, and response files (@file). --target names the target operating system and an unknown value is an error naming the accepted set. Shared objects, --Map output, response files and groups were checked to produce output. Not accepted: -T, --whole-archive, --defsym, -u, --wrap. A build that works with ld does not yet work with weld unchanged.

Archive support in weldDone. See Features above.

Mach-O objects from rasIn progress. ras writes arm64 Mach-O objects, including the ones the macOS path uses. Other Mach-O targets have not been checked.

Relocation parity in weldIn progress. Mach-O relocation handling exists in ras. The ELF path has the most depth. A PE import table is not yet complete.

Differential testing against the originalsIn progress. The ras DWARF output has been compared with GNU as by hand. No automated job compares ras with as or weld with ld.

0.3 — Depth: optimization, debugging, measurement In progress

Register allocation everywhereIn progress. Three allocators exist (--regalloc incremental|linear|graph). The default now follows what a backend implements rather than what the architecture is called: a backend with a global allocation pass takes linear at --opt-level 1 and above, and one without takes incremental. x86_64, aarch64, riscv32, riscv64, ppc64le and ppc64 have the pass, and aarch64 and riscv64 output improved substantially once they stopped being excluded by name. The difference is not measured on every backend.

Debug information on every targetIn progress. Line tables are done through ras on x86_64, AArch64 and RISC-V 64. i686 numbers instructions instead of source lines. armv7 refuses -g. Stepping and profiler attribution are not checked end to end on every target.

Vectorization with resultsIn progress. Two separate things now exist. Vectors are in the surface IR and lower on x86_64, AArch64 and WebAssembly, in a default build — a frontend can emit them and they are not experimental. The auto-vectorizer, which finds them for you, is behind the nightly feature, runs on x86_64 at --opt-level 3 only, and widens one loop shape: a self-looping element-wise block whose load and store the alias analysis proves cover the same bytes, with a constant trip count divisible by the lane count. Anything else stays scalar. Treat it as unproven: it refuses a loop at a list of guards, several of which no test exercises, and one of them was wrong until recently — a loop writing its induction variable a second time was widened as though the stride were one element. The only measured result so far is negative, for i64 on Zen 3.

Optimization-level equivalenceNot started. Each testcase program is run at the default level only, so a pass that changes behavior rather than speed would not be caught.

Emulated executionIn progress. s390x is run under QEMU user-mode as part of the recorded suite, against its cross glibc, with its output checked. It is the only cross target whose C library is installed, and so the only one that gets that far; the rest are not run at all, for want of their libraries rather than for want of an emulator.

Regressions visibleIn progress. Codegen metrics are compared against a committed baseline and a change in them is reported. Compile time and binary size are not tracked.

0.4 — Freestanding and operating-system targets Not started

Compiling for an environment the backend does not already assume: no libc, no C runtime startup objects, no host to fall back on.

Hosted and freestanding as a target propertyIn progress. Freestanding is the none environment now, not a spelling convention: it selects no libc, no startup objects and no compiler runtime, and a module that needs a runtime helper is refused at compile time naming the symbol. An operating system that supplies its own runtime declares it, so Darwin, Windows, WASI and the GPU targets take it by default. What is left is that the default weld path still supplies an interpreter of its own.

Soft floatNot started. Floating point is not lowered to a support layer for targets that disable vector units.

No red zone, strict alignmentNot started. @no_red_zone is accepted by the parser. No backend reads it. Strict alignment is not enforced.

Linker scriptsNot started. weld does not accept -T.

Done when Lamina can build a program that runs with no operating system underneath it and no C library linked into it. Artery is the driving case.

1.0 — A stable IR and a stable ABI Not started

A compatibility promise, and one that should not be made early. The IR text form and IRBuilder API stable with a documented deprecation policy. A stable C ABI. Every tested target with an end-to-end path and no system toolchain required. A correctness suite, differential testing against an established toolchain, and malformed-IR testing. Debugger integration on more than one platform.

Testing

Testing runs through every milestone rather than sitting inside one, so it gets its own section.

The rule this section exists to enforce

A target is Done only if its output is compiled, run and checked against an expected result on a machine of that architecture. Targets whose output is only read, or only assembled, are In progress or Not started, whatever they emit. Reading assembly catches a malformed instruction and nothing else; it does not catch a wrong answer.

Test tiers, added in order

Each tier is cheap to add once the one before it exists, and each catches a class of bug the earlier ones cannot.

TierStatusWhat it does, and what it catches
T0DoneUnit tests across the workspace. Logic errors inside a function.
T1DoneTestcase suite: compile, run and diff the programs in testcases/. Miscompilation, ABI mistakes, bad codegen. The benchmark programs run alongside them.
T2Not startedToolchain matrix: the same programs through GNU as and ld, through clang and lld, and through ras and weld. Divergence between our tools and the ones they replace.
T3Not startedDifferential against a C program doing the same thing. Wrong answers that are self-consistently wrong.
T4In progressDeterminism: compile twice, compare the assembly bytes. Fixed on x86_64. The other backends are not audited.
T5Not startedOptimization equivalence: every level must produce identical program output. Passes that change behavior instead of speed.
T6Not startedCross-compilation smoke: emit assembly for every recognized target name. Panics in backends nobody exercises.
T7In progressEmulated execution under QEMU. s390x runs as part of the recorded suite. The other cross targets are not run at all.
T8Not startedMalformed input: fuzz the parser and the IR validator. Panics on untrusted input.
T9In progressPerformance and size tracked per commit. Codegen metrics are tracked. Timing and binary size are not.

What stops the cross targets being run

It is not the emulator. QEMU user-mode is installed for every architecture here. What is missing is the cross C libraries, so most programs never link far enough to hand QEMU anything, and a freestanding program that does link has no startup code and faults when its entry function returns. s390x is the one architecture whose cross libc is installed here, and it is the one that runs.

Growing the suite

The programs in testcases/ cover arithmetic, control flow, calls, memory, composites, I/O, and a set of regression cases named after the bugs that produced them. That last group is the pattern to keep: every bug fixed gets a testcase named after it, added in the same change as the fix. The suite grows from real defects rather than from guesses about what might break.

Beyond that, in rough order of value: programs that mix floating point with calls, programs that stress the register allocator until it spills, deep recursion, large stack frames, structs passed and returned by value across the ABI boundary, and programs built from several translation units so linking gets exercised rather than assumed.

Decisions behind the milestones

Does a Lamina program link libc?

On a hosted target, yes. That is what the platform requires, not a compromise. The three platforms differ more than they look. Linux exposes a stable, documented syscall ABI, so a program with no libc is normal and supported, and Lamina should keep being able to produce one. macOS treats syscall numbers as unstable and expects everything to go through libSystem. Windows has no stable syscall ABI at all. Numbers change between builds, every program reaches the kernel through ntdll, and formatted I/O comes from the C runtime above it. There is no supported alternative, so calling the CRT on Windows is the only option rather than a preference.

The rule is per-target: use the platform's supported entry mechanism, and never assume the Linux one is a sensible default for anyone else.

ras replaces as, weld replaces ld, so they must behave like them

ras is an alternative to as/GAS. weld is an alternative to ld, lld, and mold. A drop-in replacement is judged against the thing it replaces: where the original has a flag, a behavior, or a diagnostic, the replacement matches it instead of inventing a nicer version, and where the original declines to do something, the replacement declines too.

ras is already built this way; its option set mirrors GAS closely. weld is further from parity in two ways.

Missing part of the ld command lineIn progress. Most common options are accepted; the list is in the table under 0.2. Not accepted: -T, --whole-archive, --defsym, -u, --wrap. -T supplies a linker script and is needed by the freestanding work, so this gap and the Artery target are the same gap.

Doing the driver's jobIn progress. ld and lld never link libc themselves. The driver does: gcc and clang add crt1.o, -lc, the dynamic-linker path, and the search paths before ld runs. Bare ld hello.o -o hello gives an unresolved printf, and that is correct behavior. On the default path, weld still supplies startup objects and a default interpreter path.

The intended end state: weld links what it is given and nothing more, and the Lamina driver assembles the CRT objects, libraries, and interpreter path from the target. A freestanding link then stops being a special case. It is simply a target whose driver adds neither, handed to a linker that never added them on its own.

Where do the I/O builtins go?

The old debug instruction and writebyte were intrinsics that each backend expands inline, with a per-OS match and a fallback arm. That design caused the Windows defect in 0.1, and it cannot express a target like Artery at all. The destination is an IR with no built-in I/O: a program declares what it calls, the target decides what that resolves to, and the backend emits an ordinary call.

In progress. @extern is done. writebyte is still a per-target builtin with a per-operating-system arm, and the arms it does not have are refusals rather than a Linux fallback: lamina.writebyte has no implementation for Unknown, and the same for Android, the console operating systems and Windows ARM64. A program that does not use it builds for those targets.

Artery

Not started. Artery is a from-scratch Rust kernel built alongside Lamina, and the reason milestone 0.4 exists. Supporting it means compiling for an environment with no libc, no startup objects, and no host underneath.

The driver parses artery as an OS name behind the nightly feature and prints it back. There is no code generation, no object emission and no linking path for it yet.

The constraints it imposes, the binary format, how system calls are reached, and the work items to get there are on their own page.

Non-goals

Replacing LLVM everywhereLamina is a backend with a small surface, and it stays that way on purpose. It is not a general-purpose replacement for every workload.

Leaking internals through the C ABINo Rust struct layouts, no MIR internals, no frozen enum discriminants.

JIT as a plugin mechanismIt exists for language implementations such as dynamic languages and bytecode VMs, not as an extension ABI.

Forcing one toolchain downstreamA frontend should be free to choose Lamina, LLVM, or something else.
