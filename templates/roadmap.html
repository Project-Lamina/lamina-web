The toolchain today

Four repositories make up the toolchain. The C bindings ship from the compiler repository with their own ABI version, deliberately independent of the crate version.

ComponentVersionRole

lamina0.0.10IR, MIR, optimizer, code generation, compiler driver.

lamina-ras0.1.2Assembler, an alternative to as/GAS. Assembly source to relocatable object.

lamina-weld0.1.1Linker, an alternative to ld/lld/mold. ELF, Mach-O, PE.

lamina-cABI 0.1.0C bindings, versioned separately from the crate.

Shipped

A typed SSA IR with a text form and an IRBuilder API. A separate machine-level IR, so target concerns stay out of the front-end-facing layer. An optimization pipeline from -O0 to -O3 covering control flow, constant folding and propagation, copy propagation, CSE, dead code, peephole, addressing, memory, strength reduction, tail calls, loop optimization, and inlining. Native code generation with no LLVM and no Cranelift. An assembler and a linker of our own. C bindings with explicit ownership. Nightly JIT compilation into executable memory.

0.1 — Correct on the targets we claim

Right now the target table makes claims nothing verifies. This milestone closes that gap and makes the self-built toolchain the default path.

Correctness

Fix Windows outputThree defects behind one symptom. writebyte falls through to a Linux syscall on every non-macOS target. The PE emitter imports every undefined symbol from kernel32.dll, but printf lives in the C runtime, so the loader cannot resolve it and the process dies before main. And no CRT library is requested for Windows links at all.

Valid RV64G from the RISC-V backendRegister use ignores the ABI's caller and callee split, x30 and x31 are taken as scratch, and division and the call sequence are wrong. The emitter should also state which extensions it assumes.

Deterministic output on every backendFixed on x86_64 by ordering register sets. The others need the same audit, because hash-ordered emission is invisible to a test that only compares program output.

Language

External function declarationsA way to declare a function the module does not define, with its ABI and attributes. This unblocks more of the rest than anything else here: it lets the I/O builtins stop being per-backend intrinsics with a Linux-shaped fallback, it is what WebAssembly needs before it can do anything observable, and it is how an Artery program will reach the kernel.

Toolchain

Move driver work out of weldweld stops supplying CRT objects and stops inventing an interpreter path. The Lamina driver supplies crt1.o, -lc, --dynamic-linker, and the search paths, derived from the target, the way gcc does before invoking ld. See the reasoning.

ras and weld as the default on x86_64 LinuxBoth already work under --assembler ras -c weld. Making them the default is the point of having written them.

Split the toolchain flags--assembler and --linker as separate choices, --compiler kept as a toolchain alias. A named tool beats an alias, an alias beats detection, and an unknown value is an error rather than a silent fallback.

Testing

Golden suite in CI on three platformsAdd windows-latest and macos-latest, and call the test runner so the 70 recorded programs are compiled, run, and diffed on every platform the table calls tested. See Testing and CI.

CI for ras, weld, and lamina-webNone of the three has any today. Plus cargo fmt --check, since the current job runs cargo fmt and commits, which hides what it should report.

Release and docs

First C bindings releaseThe source layer is done. What is missing is publication: archives with checksums, a C example rebuild in CI so exports and headers cannot drift, and the install page.

One story everywhereThe README sells four architectures as flat capabilities while the website separates tested from experimental. The website is right. Same for the nightly line: --jit and --sandbox are parsed unconditionally while the docs call the JIT nightly-only.

0.2 — A backend you can add a target to

Adding an architecture should mean implementing a trait, not editing a dozen match statements.

A codegen traitOne interface for what a backend can do: assembly output, binary output, supported options. Target selection stops being hard-coded.

Calling conventions in MIRConventions vary enough between targets to belong in the machine IR as data rather than in per-backend code.

AArch64 binary emissionAssembly workflows work. The direct binary path is still unimplemented.

ld command-line parity in weldA drop-in has to accept what it is a drop-in for. -T and -static come first, since the freestanding work depends on them. Done when a build that works with ld works with weld by substituting the binary and changing nothing else.

Archive support in weld-l is only meaningful if .a archives can be read and their members pulled in on demand, with the usual ordering and grouping rules.

Mach-O objects from rasThe Mach-O writer is a stub, so macOS still needs the system assembler.

Relocation parity in weldEqual coverage across ELF, Mach-O, and PE rather than the current ELF-first depth, and a PE path with a real import table.

Differential testing against the originalsAssemble with ras and with as, link with weld and with ld, compare. The bar is a program that behaves the same way, not one built from identical bytes. This is what keeps drop-in from being an aspiration.

0.3 — Depth: optimization, debugging, measurement

Register allocation everywhereLinear-scan and graph-coloring allocation on every backend, with the difference measured.

Debug informationDWARF line tables, enough to step through a program and attribute profiler samples.

Vectorization with resultsThe passes exist. They stay off by default until they show measured wins on the benchmark suite.

Optimization-level equivalence in CIEvery program in the suite must produce identical output at every optimization level. The cheapest check on the list, and it catches a pass that changes behavior instead of speed.

Emulated executionRISC-V and AArch64 Linux output run under QEMU, so those targets can be verified rather than eyeballed.

Regressions visible in CICompile time, generated-code performance, and binary size tracked per commit.

0.4 — Freestanding and operating-system targets

Compiling for an environment the backend does not already assume: no libc, no C runtime startup objects, no host to fall back on. Today freestanding is approximated by *_unknown, which is a gap in the vocabulary rather than a supported mode.

Hosted and freestanding as a target propertyA hosted target gets CRT objects, default libraries, and an interpreter path. A freestanding target gets none of them, and asking for them is an error rather than a silent default.

Soft floatFor targets that disable the vector units entirely, floating-point lowers to a support layer and the ABI passes floats in integer registers.

No red zone, strict alignmentBackend options honored everywhere: never use memory below the stack pointer, never emit an unaligned access.

No unwindingUnder abort-on-panic there are no unwind tables to produce and none should be required by the emitted code or the link.

Linker scriptsSection placement, load addresses, and the entry symbol from a script rather than from built-in defaults.

Done when Lamina can build a program that runs with no operating system underneath it and no C library linked into it. Artery is the driving case.

1.0 — A stable IR and a stable ABI

A compatibility promise, and one that should not be made early. The IR text form and IRBuilder API stable with a documented deprecation policy. A stable C ABI. Every tested target with an end-to-end path and no system toolchain required. A correctness suite, differential testing against an established toolchain, and malformed-IR testing. Debugger integration on more than one platform.

Testing and CI

This runs through every milestone rather than sitting inside one, so it gets its own section.

One workflow builds and tests on ubuntu-latest. Clippy and rustfmt run there too. The C SDK job has a matrix with exactly one entry. ras, weld, and lamina-web have no CI at all. Two gaps matter more than the rest.

The suite that would catch a miscompilation never runscargo test runs the unit tests and nothing else. The testcases/ directory holds 70 Lamina programs with recorded expected output and a runner that knows how to compile, run, and diff them. CI never calls it.

Nothing runs on Windows or macOSThe target table calls x86_64_windows tested and aarch64_macos partially tested, but no job has ever executed a Lamina program on either. Tested currently means someone tried it by hand once. The Windows defect below survived precisely because of this.

Smaller, but worth fixing: the rustfmt job runs cargo fmt and commits the result instead of running cargo fmt --check and failing. A formatting job that rewrites the branch hides the thing it is supposed to report.

The rule this section exists to enforce

A target may be labeled Tested only if a CI job on that operating system compiles and runs the golden suite. No exceptions, and the label comes off if the job goes away. That makes the target table above a report on CI rather than a statement of intent.

Test tiers, added in order

Each tier is cheap to add once the one before it exists, and each catches a class of bug the earlier ones cannot.

TierMilestoneWhat it does, and what it catches

T0Have itUnit tests across the workspace. Logic errors inside a function.

T10.1Golden suite: compile, run, and diff the 70 recorded programs. Miscompilation, ABI mistakes, bad codegen.

T20.2Toolchain matrix: the same programs through as+ld, clang+lld, and ras+weld. Divergence between our tools and the ones they replace.

T30.2Differential against a C program built by clang or gcc doing the same thing. Wrong answers that are self-consistently wrong.

T40.1Determinism: compile twice, compare the assembly bytes. Hash-ordered emission and other irreproducibility.

T50.3Optimization equivalence: every level must produce identical program output. Passes that change behavior instead of speed.

T60.2Cross-compilation smoke: emit assembly for every recognized triple. Panics in targets nobody exercises.

T70.3Emulated execution under QEMU. Correctness on targets with no native runner.

T81.0Malformed input: fuzz the parser and the IR validator. Panics on untrusted input.

T90.3Performance and size tracked per commit. Slow regressions nobody notices.

T5 deserves a note. It is the cheapest tier on the list and it catches the most embarrassing class of bug, because an optimization pass that changes a program's output is always wrong and is otherwise invisible until a user reports it.

Growing the suite

The 70 recorded programs cover arithmetic, control flow, calls, memory, composites, and a set of regression cases named after the bugs that produced them. That last group is the pattern to keep: every bug fixed gets a testcase named after it, added in the same change as the fix. The suite grows from real defects rather than from imagination, which is why it is worth running.

Beyond that, in rough order of value: programs that mix floating point with calls, programs that stress the register allocator past the point of spilling, deep recursion, large stack frames, structs passed and returned by value across the ABI boundary, and programs built from several translation units so linking gets exercised rather than assumed.

Decisions behind the milestones

Does a Lamina program link libc?

On a hosted target, yes. That is what the platform requires, not a compromise. The three platforms differ more than they look. Linux exposes a stable, documented syscall ABI, so a program with no libc is normal and supported, and Lamina should keep being able to produce one. macOS treats syscall numbers as unstable and expects everything to go through libSystem. Windows has no stable syscall ABI at all. Numbers change between builds, every program reaches the kernel through ntdll, and formatted I/O comes from the C runtime above it. There is no supported alternative, so calling the CRT on Windows is the only option rather than a preference.

The rule is per-target: use the platform's supported entry mechanism, and never assume the Linux one is a sensible default for anyone else.

ras replaces as, weld replaces ld, so they must behave like them

ras is an alternative to as/GAS. weld is an alternative to ld, lld, and mold. A drop-in replacement is measured against the thing it replaces: where the original has a flag, a behavior, or a diagnostic, the replacement matches it instead of inventing a nicer version, and where the original declines to do something, the replacement declines too.

ras is already built this way; its option set mirrors GAS closely. weld is further from parity in two ways.

Missing most of the ld command linePresent: -o, -e, -L, -l, --dynamic-linker, -nostdlib, plus ld64 options for Mach-O. Absent: -T, -static, -shared, --gc-sections, -z, -rpath, --start-group, --whole-archive, --Map, --defsym, --wrap, and response files. -T supplies a linker script and -static links without a dynamic loader. Both are required by the freestanding work, so this gap and the Artery target are the same gap.

Doing the driver's jobld and lld never link libc themselves. The driver does: gcc and clang add crt1.o, -lc, the dynamic-linker path, and the search paths before ld runs. Bare ld hello.o -o hello gives an unresolved printf, and that is correct behavior. weld currently supplies startup objects and hardcodes an interpreter path regardless of architecture.

The correction: weld links what it is given and nothing more, Lamina's own driver assembles the CRT objects, libraries, and interpreter path from the target, and nothing changes for the user because the driver supplies what the driver should have been supplying. A freestanding link then stops being a special case. It is simply a target whose driver adds neither, handed to a linker that never added them on its own.

Where do the I/O builtins go?

print and writebyte are intrinsics that each backend expands inline, with a per-OS match and a fallback arm. That design is the direct cause of the Windows defect below, and it cannot express a target like Artery at all. The destination is an IR with no built-in I/O: a program declares what it calls, the target decides what that resolves to, and the backend emits an ordinary call. That one change unblocks the Windows fix, WebAssembly, and Artery together.

Artery as a target

Artery is a from-scratch Rust kernel developed alongside Lamina. Its architecture treats Lamina as a backend and an LLVM alternative: an external, versioned dependency the OS is never required to use. That cuts both ways: Artery is the most demanding freestanding target Lamina has, and the best test of whether the backend works outside a hosted environment.

TargetOperatingSystem::Artery exists behind the nightly feature. The driver parses artery as an OS name and prints it back. That is the entire integration today. No code generation, no object emission, no linking path. Everything below is planned.

What the target requires

FreestandingNo libc, no CRT startup objects, no dynamic loader. The entry point is whatever the linker script says it is.

Soft floatx86_64 disables MMX, SSE, and AVX; AArch64 disables NEON and requires strict alignment. Correct code without touching the vector units.

No red zoneInterrupt handling makes it unusable, so the backend must not allocate below the stack pointer.

Abort on panicNo unwinding, so no unwind tables are needed and none should be required.

Linker script layoutSection placement comes from a script, not from linker defaults.

Binary format and system calls

Artery loads a container format of its own rather than parsing ELF in the kernel. An ELF parser on the untrusted-input path in ring 0 is a security cost the project declined to pay. Compatibility is a converter: a packing tool turns an ELF file into the container. So Lamina does not need to emit that container. A correct freestanding ELF is enough. Two consequences follow for code generation: a writable-and-executable segment is unrepresentable in the target format, so nothing Lamina emits may require one, and the capability requests a program declares are added by the packer, not by the compiler.

System calls go through declared external functions against Artery's ABI crate, not through backend-emitted syscall instructions for a hard-coded convention. That is the same underlying fix as the Windows defect in 0.1, since both are the fallback arm of an I/O intrinsic assuming Linux, and both depend on the same external-declaration work. Getting it right once serves both.

Acceptance

The Artery target is done when a program compiled by Lamina, packed into the container format, loads and runs on an Artery kernel booted under QEMU. Not when it builds, and not when a test passes. A green build of an artifact that never executes measures the parts and not the whole.

Non-goals

Replacing LLVM everywhereLamina is a backend with a deliberately small surface, not a general-purpose replacement for every workload.

Leaking internals through the C ABINo Rust struct layouts, no MIR internals, no frozen enum discriminants.

JIT as a plugin mechanismIt exists for language implementations such as dynamic languages and bytecode VMs, not as an extension ABI.

Forcing one toolchain downstreamA frontend should be free to choose Lamina, LLVM, or something else.
