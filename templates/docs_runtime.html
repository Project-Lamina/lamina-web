Runtime and libc

Lamina needs no C library and no libgcc. A program compiled from Lamina IR calls nothing you did not write, with one exception: some wide-integer and conversion operations call compiler runtime routines. Lamina ships those routines and compiles them for your target. You can also supply your own, or redirect each one to a symbol of your choice.

No libc

On Linux and macOS the compiler emits no call into libc. Instructions such as writebyte, write, read, stackalloc and the arithmetic and memory instructions are lowered to machine code or to system calls, and a program that uses none of the @extern declarations has no external symbol to resolve. Windows is the exception. It has no stable syscall numbers, so the I/O instructions call _write and _read in msvcrt, and a Windows binary always imports those.

If you want libc, declare what you need with @extern and call it. The compiler then links the symbol the way any C object would. Output and I/O shows both routes.

Compiler runtime routines

Some operations have no single machine instruction on the target. The compiler implements them with a call to a compiler runtime routine. These are the only external calls the compiler emits that you did not write. Each family comes in a 128-bit form and a 64-bit one; the 64-bit form is what an architecture whose integer registers hold 32 bits reaches for, because it splits every i64 into a register pair.

A program that reaches none of them emits none of them. Each routine is referenced by name, and nothing else is emitted without your asking.

Lamina ships them

Every routine above is written in Lamina IR and lives in builtins/ in the compiler's own source tree. When a module calls one of the names, leaves it undefined, and has not redirected it, the driver compiles that routine — and everything it calls — for the requested target and puts the objects on the link line ahead of -lc.

The driver names what it built under -v:

$ lamina div128.lamina -o div128 -v
[VERBOSE] Compiler runtime for x86_64_linux: divti3, udivti3
[VERBOSE] Linking with weld: ["div128.o", "div128.lamina-runtime/divti3.o", "div128.lamina-runtime/udivti3.o", "--dynamic-linker", "/lib64/ld-linux-x86-64.so.2", "-lc", "-o", "div128"]

The routines are ordinary IR functions with no special ABI: a 128-bit argument or result uses the same two-word convention every i128 function boundary uses. A routine the target's backend cannot compile is left out, and the symbol is resolved from the host compiler runtime instead, where the host has one.

--jit does not compile them. A program that reaches a helper takes the fallback path, which writes an executable to the cache directory and runs it, so --jit on such a program is an ahead-of-time build with an extra step.

Where these differ from libgcc

Float-to-integer conversion is undefined in libgcc for out-of-range and NaN inputs. It is defined here, and the definition is the same one the scalar fptoint contract names, so a 128-bit conversion and a 64-bit one agree.

NaNZero, on every target.

Signed, out of range__fixdfti and __fixsfti saturate: at or above 2127 gives i128::MAX, at or below -2127 and -inf give i128::MIN.

Unsigned, out of range__fixunsdfti and __fixunssfti give 0 for any negative value including -0.0, and u128::MAX at or above 2128 and for +inf.

Division by zeroTraps, as the compiler's inline 128-bit division does. __divti3(MIN, -1) and __modti3(MIN, -1) trap too; libgcc returns the wrapped value.

The 64-bit routines answer the same way at the same corners, which is what lets i686 and rv32 agree with every other backend on an fptoint rather than returning the x87 integer indefinite.

Integer-to-float rounds to nearest, ties to even, in a single rounding, and agrees with libgcc on every input. The routines were checked against an independent arbitrary-precision oracle over the tie cases, the powers of two around each rounding boundary, NaN payloads, infinities and negative zero.

libgcc is not required

No target needs it. builtins/ covers the 64-bit routines as well as the 128-bit ones, so an architecture that splits every i64 into a register pair — i686, armv7, thumbv6m, thumbv7m, riscv32 — gets its __divdi3 family from the same place a 64-bit target gets __divti3. x86_64_linux links a 128-bit program with weld alone; i686_linux divides a 64-bit integer through divdi3.o and udivdi3.o the driver built for it.

Where the host does happen to have a libgcc.a for the target, the GNU link path still names it, after the compiled objects. That is opportunistic. A missing one is not an error, and nothing is resolved from it that the shipped routines already define.

What a call looks like

This is what div.i128 lowers to. The module below divides a 128-bit value and returns the low 64 bits:

fn @main() -> i64 {
  entry:
    %a = add.i128 1, 2
    %b = div.i128 %a, 2
    %c = trunc.i128.i64 %b
    ret.i64 %c
}

On x86_64_linux the driver compiles __divti3 and __udivti3 for the target, ras assembles them, and weld links them with the program. No host assembler, linker or compiler runtime is involved. The program exits with 1.

Redirecting the routines

Set LAMINA_BUILTINS to a comma-separated list of name=symbol pairs. The name is the routine the compiler would call, and the symbol is the name it calls instead. The routine's C name is the key; the symbol is any function your program defines or links.

$ LAMINA_BUILTINS=__divti3=my_div lamina div128.lamina --emit-asm -o div128.s

The emitted code calls my_div where it would have called __divti3. The table also covers malloc, free and exit, and the C block-copy and block-fill routines: an @extern declaration of one of these names is called through the symbol you give it.

An override the compiler cannot use is an error rather than something skipped. A name that is not a routine the compiler calls is refused with the list of names that are, and an entry that is not name=symbol is refused as malformed:

$ LAMINA_BUILTINS=__nope=my_div lamina div128.lamina --emit-asm -o div128.s
Error: Validation Error: LAMINA_BUILTINS names `__nope`, which is not a runtime helper this compiler calls; the names are __divdi3, __divti3, __fixdfdi, …

$ LAMINA_BUILTINS=my_div lamina div128.lamina --emit-asm -o div128.s
Error: Validation Error: LAMINA_BUILTINS entry `my_div` is not `name=symbol`

Freestanding targets

A target whose environment is none links no C runtime and no compiler runtime, the shipped routines included. That is what freestanding means here: the link adds nothing the module did not ask for. A module that calls one of the routines above must define it itself, or name a replacement with LAMINA_BUILTINS. The compiler checks this at compile time and names the symbol in its error, instead of leaving the failure to the linker.

$ lamina div128.lamina --target x86_64_unknown --emit-asm -o div128.s
Error: "Code generation failed: Codegen Error: Unsupported feature: `__divti3` is a compiler runtime helper that a target without a C library does not provide; define it in the module, or name an implementation with LAMINA_BUILTINS=__divti3=<symbol>"

Targets are listed on Targets and backends.
