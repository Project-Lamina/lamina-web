Runtime and libc

Lamina needs no C library. A program compiled from Lamina IR calls nothing you did not write, with one exception: some 128-bit operations call compiler runtime routines. Lamina ships those routines and compiles them for your target. You can also supply your own, or redirect each one to a symbol of your choice.

No libc

The compiler emits no call into libc. Instructions such as writebyte, write, read, stackalloc and the arithmetic and memory instructions are lowered to machine code or to system calls. A program that uses none of the @extern declarations has no external symbol to resolve.

If you want libc, declare what you need with @extern and call it. The compiler then links the symbol the way any C object would. Output and I/O shows both routes.

Compiler runtime routines

Some operations have no single machine instruction on the target. The compiler implements them with a call to a compiler runtime routine. These are the only external calls the compiler emits that you did not write:

RoutineUsed forEmitted when
__divti3Signed 128-bit divisiondiv.i128
__udivti3Unsigned 128-bit divisiondiv.u128
__modti3Signed 128-bit remainderrem.i128
__umodti3Unsigned 128-bit remainderrem.u128
__floattidfSigned 128-bit integer to f64an inttofp from i128 to f64
__floatuntidfUnsigned 128-bit integer to f64an inttofp from u128 to f64
__fixdftif64 to signed 128-bit integeran fptoint from f64 to i128
__fixunsdftif64 to unsigned 128-bit integeran fptoint from f64 to u128

Conversions between f32 and 128-bit integers use four more routines of the same kind: __floattisf, __floatuntisf, __fixsfti and __fixunssfti. They are emitted only for those conversions. A program that uses no 128-bit operations emits none of these.

Each routine is referenced by name. Nothing else is emitted without your asking.

Lamina ships them

All twelve routines are written in Lamina IR and live in builtins/ in the compiler's own source tree. When a module calls one of the names above, leaves it undefined, and has not redirected it, the driver compiles that routine — and everything it calls — for the requested target and puts the objects on the link line ahead of -lc. A program that reaches none of the twelve builds exactly as it did before.

The driver names what it built under -v:

$ lamina div128.lamina -o div128 -v
[VERBOSE] Compiler runtime for x86_64_linux: divti3, udivti3
[VERBOSE] Linking with weld: ["div128.o", "div128.lamina-runtime/divti3.o", "div128.lamina-runtime/udivti3.o", "-lc", "-o", "div128"]

The routines are ordinary IR functions with no special ABI: a 128-bit argument or result uses the same two-word convention every i128 function boundary uses. A routine the target's backend cannot compile is left out, and the symbol is resolved from the host compiler runtime instead.

--jit does not compile them. A program that reaches a 128-bit helper takes the fallback path, which writes an executable to the cache directory and runs it, so --jit on such a program is an ahead-of-time build with an extra step.

Where these differ from libgcc

Float-to-integer conversion is undefined in libgcc for out-of-range and NaN inputs. It is defined here, and the definition is the same one the scalar fptoint contract names, so a 128-bit conversion and a 64-bit one agree.

NaNZero, on every target.

Signed, out of range__fixdfti and __fixsfti saturate: at or above 2127 gives i128::MAX, at or below -2127 and -inf give i128::MIN.

Unsigned, out of range__fixunsdfti and __fixunssfti give 0 for any negative value including -0.0, and u128::MAX at or above 2128 and for +inf.

Division by zeroTraps, as the compiler's inline 128-bit division does. __divti3(MIN, -1) and __modti3(MIN, -1) trap too; libgcc returns the wrapped value.

Integer-to-float rounds to nearest, ties to even, in a single rounding, and agrees with libgcc on every input. The routines were checked against an independent arbitrary-precision oracle over the tie cases, the powers of two around each rounding boundary, NaN payloads, infinities and negative zero.

Where libgcc is still required

builtins/ holds 128-bit routines and no 64-bit ones. An architecture whose integer registers are narrower than 64 bits splits every i64 into a register pair and needs the __divdi3 family, which is not ours. On those targets the host toolchain's libgcc.a is required beside the shipped routines, and a link that cannot find it is an error naming the compiler it looked in: i686, armv7, thumbv6m, thumbv7m and riscv32.

On a 64-bit target nothing from libgcc is required. x86_64_linux links a 128-bit program with weld alone.

What a call looks like

This is what div.i128 lowers to. The module below divides a 128-bit value and returns the low 64 bits:

fn @main() -> i64 {
  entry:
    %a = add.i128 1, 2
    %b = div.i128 %a, 2
    %c = trunc.i128.i64 %b
    ret.i64 %c
}

On x86_64_linux the driver compiles __divti3 and __udivti3 for the target, ras assembles them, and weld links them with the program. No host assembler, linker or compiler runtime is involved. The program exits with 1.

Redirecting the routines

Set LAMINA_BUILTINS to a comma-separated list of name=symbol pairs. The name is the routine the compiler would call, and the symbol is the name it calls instead. The routine's C name is the key; the symbol is any function your program defines or links.

$ LAMINA_BUILTINS=__divti3=my_div lamina div128.lamina --emit-asm -o div128.s

The emitted code calls my_div where it would have called __divti3. The table also covers malloc, free and exit, and the C block-copy and block-fill routines: an @extern declaration of one of these names is called through the symbol you give it.

Freestanding targets

A target whose environment is none links no C runtime and no compiler runtime, the shipped routines included. That is what freestanding means here: the link adds nothing the module did not ask for. A module that calls one of the routines above must define it itself, or name a replacement with LAMINA_BUILTINS. The compiler checks this at compile time and names the symbol in its error, instead of leaving the failure to the linker.

$ lamina div128.lamina --target x86_64_unknown --emit-asm -o div128.s
Error: "Code generation failed: Codegen Error: Unsupported feature: `__divti3` is a compiler runtime helper that a target without a C library does not provide; define it in the module, or name an implementation with LAMINA_BUILTINS=__divti3=<symbol>"

Targets are listed on Targets and backends.
